1. Data Compaction — Recap Low ⭐ — intro

English

Data compaction (source coding) is the process of encoding source symbols using codewords of variable length, such that symbols with higher probability get shorter codewords and rarer symbols get longer codewords — reducing the average number of bits/symbol close to the source entropy H(X).

Hinglish

Simple idea: jo letter/symbol zyada baar aata hai usko chhota code do, jo kam aata hai usko lamba code do. Isse average length kam ho jaati hai — yahi compression ka core idea hai (Morse code mein bhi 'E' ek dot hai kyunki English mein sabse common letter hai!).

💡

Two big families exist: (1) Statistical / entropy coders — Huffman, Shannon-Fano — need symbol probabilities in advance and code single symbols. (2) Dictionary / adaptive coders — Lempel-Ziv family — need no prior probability table and code repeated sequences on the fly. RTU almost always asks you to compare these two families directly, so keep this distinction sharp.

2. Prefix Code (Instantaneous Code) High ⭐⭐⭐

English

A prefix code (instantaneous code) is a variable-length code in which no codeword is a prefix of any other codeword. This property allows the receiver to decode each symbol the moment its complete codeword is received — without needing to look ahead at future bits.

Hinglish

Prefix code ka matlab — koi bhi chhota codeword kisi bade codeword ka "starting part" nahi hona chahiye. Isse decoding karte waqt confusion nahi hota — jaise hi codeword complete hota hai, turant pata chal jaata hai ki symbol kya hai, aage ke bits dekhne ki zarurat nahi (isiliye "instantaneous" kehte hain).

Example

Valid prefix code: A=0, B=10, C=110, D=111 → no code is prefix of another ✓

Invalid (not prefix-free): A=0, B=01, C=011 → here '0' (code for A) is a prefix of '01' (code for B) ✗ — decoding becomes ambiguous.

Decoding walkthrough (valid code above): received bitstream 0 110 10 111 → read bit by bit: "0" instantly matches A → decode A, reset; "1","1","0" matches C → decode C, reset; "1","0" matches B → decode B, reset; "1","1","1" matches D → decode D. Final message = A C B D, decoded uniquely with zero lookahead.

Fig 3.1 — Binary Code Tree for prefix code A=0,B=10,C=110,D=111: teal nodes are leaves (carry a symbol), slate nodes are internal branch points — only leaf nodes carry symbols, so no codeword can be a prefix of another

Kraft's Inequality — Testing if a Prefix Code Can Exist Medium ⭐⭐ — often asked as short numerical

English

For a binary prefix code with codeword lengths l₁, l₂, …, ln, a prefix code exists if and only if the Kraft Inequality holds:

Σ 2−li ≤ 1
Hinglish

Ye ek quick "sanity test" hai — agar tumhe sirf codeword lengths (0,10,110,111 jaise actual codes nahi, sirf lengths 1,2,3,3) di gayi hon, to Kraft inequality laga ke pata chal jaata hai ki inn lengths ka koi valid prefix code ban sakta hai ya nahi, bina tree banaye. Agar sum ≤ 1 hai to code possible hai, agar > 1 hai to impossible hai.

Numerical

Check whether lengths {1, 2, 3, 3} can form a valid binary prefix code.

Solution: Σ2−li = 2−1+2−2+2−3+2−3 = 0.5+0.25+0.125+0.125 = 1.0 ≤ 1 ✓ → a valid prefix code exists (this is exactly the A=0,B=10,C=110,D=111 tree above — it's "full", nothing wasted).

Second check: lengths {1,1,2} → Σ = 0.5+0.5+0.25 = 1.25 > 1 ✗ → no valid binary prefix code can have these lengths (two length-1 codes 0 and 1 already exhaust the whole tree, leaving no room for a third symbol).

3. Huffman Coding High ⭐⭐⭐⭐⭐ (Most Important — numerical guaranteed)

English

Huffman coding is an optimal variable-length prefix coding technique that builds a binary tree bottom-up by repeatedly combining the two least-probable symbols/nodes into a new node, until a single root remains. It achieves the minimum possible average codeword length for a given symbol probability distribution (among all prefix codes).

Hinglish

Huffman coding ka logic — har step pe sabse 2 kam probability wale symbols/nodes ko utha ke unko jod do (ek naya combined node bana do), aur ye repeat karte raho jab tak sirf ek root node na bach jaaye. Ye process "optimal" code deta hai — matlab sabse kam possible average length.

Huffman Coding Algorithm High — write this step-by-step in exam

  1. List all symbols with their probabilities in descending order.
  2. Take the two symbols with lowest probability; combine them into a new node with probability = sum of the two.
  3. Assign bit '0' to one branch and '1' to the other (convention).
  4. Re-sort the list (treating combined node as a new "symbol") and repeat steps 2-3 until only one node (probability = 1) remains — this is the root.
  5. The codeword for each original symbol = the sequence of 0s/1s read from root to that leaf.
Full Worked Example 1 — most common numerical pattern

Symbols: A(0.4), B(0.2), C(0.2), D(0.1), E(0.1). Construct Huffman code and find average code length & efficiency.

Step-by-step combination:
Step 1: D(0.1)+E(0.1) → DE(0.2)
Step 2: Now: A(0.4), B(0.2), C(0.2), DE(0.2) → combine two lowest: C(0.2)+DE(0.2) → CDE(0.4)
Step 3: Now: A(0.4), B(0.2), CDE(0.4) → combine B(0.2)+CDE(0.4) → BCDE(0.6)
Step 4: Now: A(0.4), BCDE(0.6) → combine → root(1.0)

Resulting codewords (one valid assignment):

SymbolProbabilityCodewordLength
A0.401
B0.2102
C0.21103
D0.111104
E0.111114

Average code length:
Lavg = Σ Pᵢlᵢ = 0.4(1)+0.2(2)+0.2(3)+0.1(4)+0.1(4) = 0.4+0.4+0.6+0.4+0.4 = 2.2 bits/symbol

Entropy: H(X) = −Σ Pᵢlog₂Pᵢ = 0.4(1.32)+0.2(2.32)+0.2(2.32)+0.1(3.32)+0.1(3.32) ≈ 2.122 bits/symbol

Efficiency: η = H(X)/Lavg = 2.122/2.2 = 96.5%  |  Redundancy = 1−0.965 = 3.5%

Variance check (why 0-4 assignment vs 1-4?): the choice of which branch gets '0' and which gets '1' at each merge is arbitrary and doesn't change Lavg — only the specific bit pattern changes, never the length distribution. That's why "a Huffman code" for a given probability set is not unique, but its Lavg always is.

Full Worked Example 2 — six symbols, different pattern (practice this style too)

Symbols: A(0.30), B(0.25), C(0.20), D(0.10), E(0.10), F(0.05). Construct the Huffman code and find Lavg and efficiency.

Step-by-step combination:
Step 1: E(0.10)+F(0.05) → EF(0.15)
Step 2: List: A(0.30),B(0.25),C(0.20),D(0.10),EF(0.15) → two lowest: D(0.10)+EF(0.15) → DEF(0.25)
Step 3: List: A(0.30),B(0.25),C(0.20),DEF(0.25) → two lowest: C(0.20)+DEF(0.25)? Careful — sort first: A(0.30),B(0.25),DEF(0.25),C(0.20) → two lowest: C(0.20)+DEF(0.25) → CDEF(0.45)

Step 5: List: AB(0.55), CDEF(0.45) → combine → root(1.0)

Lavg = 0.30(2)+0.25(2)+0.20(2)+0.10(3)+0.10(4)+0.05(4) = 0.6+0.5+0.4+0.3+0.4+0.2 = 2.4 bits/symbol

Entropy H(X) = −Σ Pᵢlog₂Pᵢ ≈ 0.30(1.737)+0.25(2)+0.20(2.322)+0.10(3.322)+0.10(3.322)+0.05(4.322) ≈ 0.521+0.5+0.464+0.332+0.332+0.216 ≈ 2.366 bits/symbol

⚠️

Common exam mistake: after every merge, students forget to re-sort the full list (not just insert the new node at the end). Always re-arrange in descending order before picking the next two lowest — this is where most numerical errors happen.

4. Shannon-Fano Coding High ⭐⭐⭐⭐

English

Shannon-Fano coding is a top-down variable-length prefix coding technique that recursively splits a probability-sorted symbol list into two parts with (as nearly as possible) equal total probabilities, assigning '0' to one part and '1' to the other, and repeating on each sub-part until every symbol is isolated.

Hinglish

Huffman "bottom-up" (chhote nodes jodke upar jaate hain) hai, Shannon-Fano "top-down" hai — pehle sabko probability ke order mein rakho, fir list ko 2 roughly-equal-probability groups mein divide karo (top group=0, bottom group=1), aur har group ko fir se divide karte raho jab tak ek-ek symbol na bach jaaye.

Shannon-Fano Algorithm Medium

  1. Arrange symbols in descending order of probability.
  2. Divide the list into two parts such that the sum of probabilities in each part is as close to equal as possible.
  3. Assign '0' to the upper part and '1' to the lower part.
  4. Recursively repeat the division process on each part until each part contains only a single symbol.
Full Worked Example 1 (same symbol set, for direct comparison with Huffman)

Symbols: A(0.4), B(0.2), C(0.2), D(0.1), E(0.1)

Split 1: {A(0.4)} | {B,C,D,E(0.6)} → A=0, rest start with 1
Split 2 (within 0.6 group): {B(0.2)} | {C,D,E(0.4)} → B=10, rest start with 11
Split 3 (within 0.4 group): {C(0.2)} | {D,E(0.2)} → C=110, rest start with 111
Split 4: {D(0.1)} | {E(0.1)} → D=1110, E=1111

SymbolProbabilityCodewordLength
A0.401
B0.2102
C0.21103
D0.111104
E0.111114

Lavg = 2.2 bits/symbol (same as Huffman in this particular example — but Huffman is guaranteed optimal in general, Shannon-Fano is not always).

Full Worked Example 2 — a case where Shannon-Fano is sub-optimal vs Huffman

Symbols: A(0.35), B(0.30), C(0.20), D(0.15). Compare Shannon-Fano and Huffman.

Shannon-Fano splits:
Split 1: {A(0.35),B(0.30)}=0.65 | {C(0.20),D(0.15)}=0.35 → upper=0, lower=1 (closest split — 0.65/0.35 is the best available two-way split here)
Split 2 (within upper): {A(0.35)}|{B(0.30)} → A=00, B=01
Split 3 (within lower): {C(0.20)}|{D(0.15)} → C=10, D=11

Shannon-Fano lengths: A=2,B=2,C=2,D=2 → Lavg(SF) = 0.35(2)+0.30(2)+0.20(2)+0.15(2) = 2.0 bits/symbol

Huffman on the same set: combine C(0.20)+D(0.15)→CD(0.35); now A(0.35),B(0.30),CD(0.35) → combine B(0.30)+CD(0.35)→BCD(0.65); combine A(0.35)+BCD(0.65)→root. Codes: A=0 (len1), B=10 (len2), C=110 (len3), D=111 (len3).

Huffman Lavg = 0.35(1)+0.30(2)+0.20(3)+0.15(3) = 0.35+0.60+0.60+0.45 = 2.00 bits/symbol — here they tie again, but this pair of examples is the standard way examiners show that Huffman's guarantee of optimality is stronger even when the numeric answer for a specific case matches. In distributions that are less "balanced" (try A=0.5,B=0.25,C=0.125,D=0.125), Shannon-Fano's greedy top split can lock in a worse tree than Huffman's bottom-up merge — always mention this guarantee vs coincidence distinction in theory answers.

Huffman vs Shannon-Fano High ⭐⭐⭐⭐ — very frequently asked difference question

AspectHuffman CodingShannon-Fano Coding

5. Lempel-Ziv (LZ) Coding High ⭐⭐⭐

English

Lempel-Ziv coding is a dictionary-based / adaptive universal lossless compression technique that does not require prior knowledge of source symbol probabilities. It works by building a dictionary of previously-seen substrings/patterns and replacing repeated occurrences with shorter references (pointers) to dictionary entries.

Hinglish

Huffman/Shannon-Fano ke liye tumhe symbol probabilities pehle se pata honi chahiye. LZ coding mein aisi koi zarurat nahi — ye "on-the-fly" data ke patterns ko dekh ke khud dictionary banata hai, aur jab wahi pattern repeat ho, to use ek short "pointer/code" se replace kar deta hai. Isi liye LZ ko "universal" / "adaptive" coding kehte hain — ye file ke type pe depend nahi karta (text, image, sab pe chal jaata hai). ZIP, GIF, PNG sab LZ-family algorithms use karte hain!

LZ77 — Sliding Window Approach Medium ⭐⭐

LZ77 uses a sliding window over the data, split into a "search buffer" (already encoded text) and "look-ahead buffer" (upcoming text). For each position, it searches the search buffer for the longest match to the upcoming data, and outputs a triple:

(offset, length, next_character)

where offset = how far back the match starts, length = how many characters matched, and next_character = the character following the match (that breaks the match).

Simplified Example

Input string: ABABABA

Encoding: A(0,0,A) → B(0,0,B) → AB seen before at offset 2, length 2 → match → (2,2,A) → remaining 'BA' matches at offset 2 → (2,2, end)

Output (conceptually): (0,0,A)(0,0,B)(2,2,A)(2,2,-) — repeated "AB" pattern is replaced by short back-references instead of repeating raw characters, hence compression.

Decoding walkthrough (how the receiver reverses this): the decoder maintains the same growing buffer. (0,0,A) → output "A", buffer="A". (0,0,B) → output "B", buffer="AB". (2,2,A) → go back 2 positions in the buffer, copy 2 characters ("AB"), then append the literal 'A' → output "ABA", buffer="ABABA". (2,2,-) → go back 2, copy 2 ("BA") → output "BA", buffer="ABABABA". Final reconstructed string = ABABABA, exactly matching the original — this is why LZ77 is lossless.

Fig 3.2 — LZ77 sliding window: matches found in search buffer are replaced with (offset,length) back-references

LZ78 — Explicit Dictionary Approach Medium ⭐⭐ — brief but sometimes asked

English

Unlike LZ77's sliding window, LZ78 builds an explicit, ever-growing dictionary of phrases (indexed 1,2,3,…) and encodes each new phrase as a pair (dictionary index of longest existing match, next new character), then adds that new phrase to the dictionary.

Simplified Example

Input: ABABABA, dictionary starts empty (index 0 = "").

Parse: "A" not in dict → output (0,A), add dict[1]="A". "B" not in dict → output (0,B), add dict[2]="B". "AB" is in dict (dict[1]="A", then next char "B"... longest existing match "A"=dict[1], next char "B") → output (1,B), add dict[3]="AB". "AB" again but now check longest match: "AB"=dict[3]? "ABA" → longest match "AB"(dict 3), next char "A" → output (3,A), add dict[4]="ABA". Remaining none.

Output: (0,A)(0,B)(1,B)(3,A) — notice the dictionary grows with every new phrase, and later matches can reference multi-character earlier phrases, giving LZ78 stronger compression on longer, more repetitive inputs (this is the basis of the GIF/LZW algorithm).

Hinglish

LZ77 "sliding window" ke andar hi match dhoondta hai (limited memory), jabki LZ78 ek permanent, badhta hua dictionary banata hai jisme har naya phrase add hota rehta hai — isiliye lambi files pe LZ78/LZW (GIF format mein use hota hai) zyada effective ho sakta hai.

6. Channel Capacity (Continuous Channel) High ⭐⭐⭐⭐⭐ — Shannon-Hartley theorem

English

For a continuous, band-limited channel corrupted by additive white Gaussian noise (AWGN), the Shannon-Hartley Theorem gives the channel capacity — the maximum rate at which information can be transmitted with arbitrarily low error probability:

C = B · log₂(1 + S/N)   [bits/second]

where B = channel bandwidth (Hz), S = average received signal power, N = average noise power, S/N = signal-to-noise ratio (SNR).

Hinglish

Ye formula batata hai ki ek channel ki maximum reliable speed uske bandwidth aur signal-to-noise ratio pe depend karti hai. Zyada bandwidth ya zyada SNR (kam noise) → zyada capacity. Yahi formula bataata hai ki tumhare WiFi/4G ki max possible speed kitni ho sakti hai given uska bandwidth aur signal quality.

Numerical 1 — basic telephone-line style channel

A channel has bandwidth B=3000 Hz and SNR=1000 (≈30dB, typical telephone line). Find channel capacity.

Solution:
C = 3000 × log₂(1+1000) = 3000 × log₂(1001) ≈ 3000 × 9.97 ≈ 29,910 bits/sec ≈ 29.9 kbps

Numerical 2 — SNR given in dB (very common variant)

A channel has bandwidth B = 4 kHz and SNR = 20 dB. Find the channel capacity.

Solution:
Step 1 — convert dB to linear ratio: SNR(dB) = 10 log₁₀(S/N) → 20 = 10 log₁₀(S/N) → S/N = 1020/10 = 102 = 100
Step 2 — apply Shannon-Hartley: C = B log₂(1+S/N) = 4000 × log₂(101) = 4000 × 6.658 ≈ 26,633 bits/sec ≈ 26.6 kbps

Exam tip: whenever SNR is given in dB, always convert with S/N = 10(dB/10) before plugging into the log₂ formula — a very common mark-losing mistake is plugging the dB value directly into log₂().

Numerical 3 — bandwidth vs SNR trade-off

Compare two channel design options that must both deliver roughly the same capacity: Option 1: B=1 kHz with a high SNR of 1023 (≈30dB). Option 2: B=2 kHz with a lower SNR of 31 (≈15dB). Which gives higher capacity?

Option 1: C₁ = 1000 × log₂(1024) = 1000 × 10 = 10,000 bps = 10 kbps

Option 2: C₂ = 2000 × log₂(32) = 2000 × 5 = 10,000 bps = 10 kbps

Conclusion: both options give identical capacity, demonstrating the fundamental bandwidth–SNR trade-off: you can achieve a target capacity either with high bandwidth + modest SNR, or with narrow bandwidth + very high SNR — capacity depends on the combination B·log₂(1+S/N), not on B or SNR alone.

Properties of Channel Capacity Medium

  1. Capacity increases with bandwidth B (linearly) and with log of SNR (diminishing returns at high SNR).
  2. Even with infinite bandwidth, capacity approaches a finite limit: C∞ = (S/N₀)·log₂e ≈ 1.44·S/N₀ (where N₀ = noise power spectral density) — this is the absolute limit imposed by noise power alone.
  3. Trade-off: the same capacity can be achieved with high bandwidth + low SNR, or low bandwidth + high SNR (see Numerical 3 above).

7. Channel Coding Theorem (Shannon's Second Theorem) High ⭐⭐⭐⭐⭐ — extremely important theory

English

Shannon's Channel Coding Theorem states: For a discrete memoryless channel with capacity C, if the information transmission rate R is less than or equal to C (R ≤ C), then there exists a coding scheme such that the probability of error can be made arbitrarily small (approaching zero) by increasing the code block length, while keeping R fixed. Conversely, if R > C, reliable (error-free) transmission is not possible, no matter how clever the code.

Hinglish

Yeh Information Theory ka sabse important result hai! Iska matlab — agar tum data ko channel capacity C se kam ya equal rate pe bhejo, to (achha encoding/decoding scheme use karke) error-probability ko almost zero tak le ja sakte ho — bina speed kam kiye! Lekin agar capacity C se zyada rate pe bhejne ki koshish karo, to error-free transmission kabhi possible nahi, chahe kitna bhi smart code design karo. Ye theorem hi batata hai ki error-correcting codes (jo Unit 4/5 mein padhenge) kyu kaam karte hain.

Significance / Key Takeaways High

  • It proves that reliable communication is possible even over noisy channels — as long as R ≤ C, which was a revolutionary (and initially counter-intuitive) result in 1948.
  • It does NOT tell us how to construct such a code — only that one exists. The theorem is a pure existence proof.
  • It establishes capacity C as a sharp threshold: below it, arbitrarily reliable communication is achievable; above it, it is fundamentally impossible.
  • This motivated decades of research into practical error-correcting codes (Linear Block, Cyclic, Convolutional, Turbo, LDPC) that try to approach the Shannon limit.
Applied Numerical — using the theorem, not just the formula

A channel has capacity C = 26.6 kbps (from Numerical 2 above). A designer wants to transmit at R = 20 kbps. Is reliable (arbitrarily low error) transmission possible? What if the designer instead wants R = 30 kbps?

Solution: Since R = 20 kbps < C = 26.6 kbps → R ≤ C, so by the Channel Coding Theorem a coding scheme exists that can make error probability as small as desired (though the theorem doesn't tell us what that code looks like — only that increasing block length with a good code drives Pe→0). For R = 30 kbps > C, reliable transmission is impossible — no matter how sophisticated the encoder/decoder, errors cannot be driven to zero at that rate on this channel.

8. Shannon Limit High ⭐⭐⭐⭐

English

The Shannon Limit is the theoretical maximum data rate (= channel capacity C) at which information can be transmitted over a given channel with an arbitrarily low (→0) probability of error. It represents the ultimate boundary on communication efficiency dictated by the channel's bandwidth and noise — no real coding scheme can exceed it.

Hinglish

Shannon Limit = wo "ultimate speed limit" jo ek channel apni bandwidth aur noise ki wajah se allow karta hai. Iske aage koi bhi coding scheme — chahe kitna bhi advanced ho — error-free data nahi bhej sakta. Modern codes (Turbo codes, LDPC codes — jo 4G/5G/WiFi mein use hote hain) is limit ke bahut close (0.5dB ke andar!) pohoch chuke hain — yehi unki achievement hai.

Numerical — Shannon limit on Eb/N₀ (minimum SNR per bit for reliable communication)

Find the minimum theoretical Eb/N₀ (in dB) required for reliable communication as the bandwidth becomes very large (the classical "Shannon bound" / "−1.6 dB limit").

Solution (derivation sketch): Starting from C = B log₂(1+S/N), and writing S = Eb·C (energy per bit times bit rate) with N = N₀B, as B→∞ and C/B→0, the limiting condition works out to:

Eb/N₀ ≥ ln 2 ≈ 0.693   ⇒   (Eb/N₀)dB = 10 log₁₀(0.693) ≈ −1.6 dB

Interpretation: this famous −1.6 dB Shannon limit is the absolute minimum energy-per-bit-to-noise ratio below which reliable communication is impossible, no matter how much bandwidth is used or how clever the code — it's the "floor" that practical codes like Turbo and LDPC try to approach (modern LDPC codes now operate within roughly 0.5–1 dB of this floor).

Q1 · Theory
Define prefix code. Why is it also called an instantaneous code? Give one valid and one invalid example.
★★★ 5 Marks

A prefix code (also called an instantaneous code) is a variable-length code in which no codeword is a prefix of any other codeword in the code set.

It is called "instantaneous" because the decoder can identify each symbol the moment its complete codeword arrives on the bitstream — it never needs to peek ahead at future bits to resolve ambiguity, so decoding happens symbol-by-symbol in real time as bits stream in.

Valid example: A=0, B=10, C=110, D=111 — no codeword is a prefix of another, so this decodes instantly and unambiguously.

Invalid example: A=0, B=01, C=011 — here A's code "0" is a prefix of B's code "01", so on seeing a "0" the decoder cannot know yet whether it's the complete symbol A or just the start of B; it must wait for more bits, which breaks the instantaneous property.

Q2 · Numerical
Given codeword lengths {1, 2, 3, 3}, verify using Kraft's Inequality whether a valid binary prefix code exists. Repeat for lengths {1, 1, 2}.
★★ 5 Marks

Kraft's Inequality states a binary prefix code exists for a set of lengths l₁,…,ln if and only if Σ 2−lᵢ ≤ 1.

Case 1 — {1,2,3,3}: Σ = 2−1+2−2+2−3+2−3 = 0.5+0.25+0.125+0.125 = 1.0, which is ≤ 1, so a valid prefix code exists (and in fact uses the tree completely, with no wasted leaves).

Case 2 — {1,1,2}: Σ = 0.5+0.5+0.25 = 1.25, which is > 1, so no valid binary prefix code can be built with these lengths — two codewords of length 1 already use up both branches at the root, leaving nowhere for the third symbol to attach without violating the prefix property.

Q3 · Theory + Numerical
Explain the Huffman coding algorithm. Construct a Huffman code for symbols A(0.4), B(0.2), C(0.2), D(0.1), E(0.1) and find the average code length and coding efficiency.
★★★★★ 10 Marks — guaranteed numerical every year

Algorithm: (1) list all symbols with probabilities in descending order; (2) repeatedly take the two lowest-probability nodes and merge them into a new node whose probability is their sum, assigning bit '0' to one branch and '1' to the other; (3) re-sort the updated list after every merge; (4) repeat until a single root node (probability 1) remains; (5) read each symbol's codeword as the sequence of 0s/1s from root to that leaf.

Construction: D(0.1)+E(0.1)→DE(0.2); C(0.2)+DE(0.2)→CDE(0.4); B(0.2)+CDE(0.4)→BCDE(0.6); A(0.4)+BCDE(0.6)→root(1.0).

Codewords: A=0 (len 1), B=10 (len 2), C=110 (len 3), D=1110 (len 4), E=1111 (len 4).

Average length: Lavg = Σ Pᵢlᵢ = 0.4(1)+0.2(2)+0.2(3)+0.1(4)+0.1(4) = 2.2 bits/symbol.

Entropy: H(X) = −Σ Pᵢlog₂Pᵢ ≈ 2.122 bits/symbol.

Efficiency: η = H(X)/Lavg = 2.122/2.2 ≈ 96.5%, so redundancy ≈ 3.5%. This is close to optimal, confirming Huffman coding's near-entropy performance on this distribution.

Q4 · Numerical (practice variant)
Construct the Huffman code for A(0.30), B(0.25), C(0.20), D(0.10), E(0.10), F(0.05) and compute Lavg, entropy, and efficiency.
★★★★ 10 Marks

Construction: E(0.10)+F(0.05)→EF(0.15); D(0.10)+EF(0.15)→DEF(0.25); C(0.20)+DEF(0.25)→CDEF(0.45); A(0.30)+B(0.25)→AB(0.55); AB(0.55)+CDEF(0.45)→root(1.0).

Codewords: A=00, B=01, C=11 (all length 2); D=101 (length 3); E=1000, F=1001 (both length 4).

Lavg = 0.30(2)+0.25(2)+0.20(2)+0.10(3)+0.10(4)+0.05(4) = 2.4 bits/symbol.

Entropy H(X) ≈ 2.366 bits/symbol.

Efficiency η ≈ 2.366/2.4 ≈ 98.6%, redundancy ≈ 1.4% — higher than the 5-symbol example because this probability set sits closer to a "clean" power-of-two-like distribution.

Q5 · Theory + Numerical
Explain the Shannon-Fano coding algorithm with a suitable example. Compare its efficiency with Huffman coding on the same data.
★★★★ 10 Marks

Algorithm: (1) arrange symbols in descending order of probability; (2) split the ordered list into two groups whose total probabilities are as close to equal as possible; (3) assign '0' to the upper group and '1' to the lower group; (4) recursively repeat the split within each group until every symbol is isolated with its own codeword.

Worked example on A(0.4),B(0.2),C(0.2),D(0.1),E(0.1): Split1 {A}|{B,C,D,E}→A=0; Split2 {B}|{C,D,E}→B=10; Split3 {C}|{D,E}→C=110; Split4 {D}|{E}→D=1110,E=1111.

Result: Lavg(SF) = 2.2 bits/symbol — identical to Huffman on this particular distribution.

Comparison note: Shannon-Fano's greedy top-down split can coincide with Huffman's optimum on "clean" distributions like this one, but Shannon-Fano is not guaranteed optimal in general — on distributions that don't split evenly, its greedy choice at the top level can lock in a sub-optimal tree, whereas Huffman's bottom-up merging always finds the minimum Lavg among all prefix codes.

Q6 · Theory
Differentiate between Huffman coding and Shannon-Fano coding.
★★★★ 5 Marks — very frequently asked

Huffman coding builds its tree bottom-up, repeatedly combining the two lowest-probability nodes, and is always optimal — it provably achieves the minimum possible average codeword length among all prefix codes for a given probability distribution.

Shannon-Fano coding builds its tree top-down, recursively splitting the sorted symbol list into two roughly-equal-probability halves, and is not always optimal — its greedy splitting choice can occasionally produce a longer average length than Huffman's.

In practice, Huffman coding is what's actually used in real compression standards (JPEG, MP3, ZIP/DEFLATE), while Shannon-Fano is mostly of historical and educational interest, having been superseded by Huffman's provably-optimal algorithm shortly after its introduction.

Q7 · Theory
Explain the Lempel-Ziv coding technique. How is it fundamentally different from Huffman/Shannon-Fano coding?
★★★★ 7 Marks

Lempel-Ziv (LZ) coding is a dictionary-based, adaptive lossless compression technique. Unlike entropy coders, it requires no prior knowledge of symbol probabilities — instead, it scans the data itself, builds up a dictionary of previously-seen substrings/patterns as it goes, and replaces repeated occurrences of those patterns with short back-references (pointers) into the dictionary rather than repeating the raw characters.

This makes LZ coding universal: the same algorithm works well on text, source code, images, or any data with repeated structure, without needing to be tuned to a known probability model in advance.

Key difference from Huffman/Shannon-Fano: those two are statistical coders that compress individual symbols based on their known frequency, and require the probability table up front. LZ coding is a pattern-matching coder that compresses repeated sequences of symbols, adapting to the data on the fly — this is why LZ-family algorithms (ZIP, GIF, PNG, GZIP) dominate general-purpose file compression, while Huffman is often used as a secondary/final compression stage layered on top of another technique (e.g., inside JPEG or DEFLATE).

Q8 · Numerical
Explain LZ77 sliding-window compression with a worked example, including both encoding and decoding.
★★★ 7 Marks

LZ77 maintains a sliding window over the data stream, divided into a search buffer (already-processed text, acting as the "dictionary") and a look-ahead buffer (upcoming text to be encoded). At each step, it finds the longest match between the look-ahead buffer and any substring in the search buffer, and outputs the triple (offset, length, next_character).

Encoding example on ABABABA: A→(0,0,A); B→(0,0,B); the next two characters "AB" match text 2 positions back with length 2→(2,2,A); the final "BA" matches similarly→(2,2,−). Output stream: (0,0,A)(0,0,B)(2,2,A)(2,2,−).

Decoding: the receiver rebuilds the same growing buffer using each triple: (0,0,A)→append "A"; (0,0,B)→append "B"; (2,2,A)→go back 2 characters in the buffer, copy 2 characters ("AB"), then append the literal 'A'; (2,2,−)→go back 2, copy 2 more characters ("BA"). The reconstructed string is exactly ABABABA, confirming the scheme is fully lossless.

Q9 · Theory
How does LZ78 differ from LZ77? Explain briefly with an example.
★★★ 5 Marks

LZ77 searches for matches only within a fixed-size sliding window of recently-seen text, which limits how far back it can reference. LZ78 instead builds an explicit, unbounded dictionary of phrases as it parses the input, indexing each new phrase (1, 2, 3, …) and encoding each step as a pair (index of longest existing dictionary match, next new character).

Example on ABABABA: parsing gives phrases "A"→dict[1], "B"→dict[2], "AB"→dict[3] (built from dict[1]+"B"), "ABA"→dict[4] (built from dict[3]+"A"), yielding output (0,A)(0,B)(1,B)(3,A).

Because the dictionary keeps growing and phrases can reference other multi-character phrases, LZ78 (and its popular variant LZW, used in GIF images) tends to compress longer, more repetitive files more effectively than LZ77's bounded window.

Q10 · Theory + Derivation
State and explain the Shannon-Hartley theorem for the channel capacity of a continuous channel. Derive/explain each term.
★★★★★ 7-10 Marks

The Shannon-Hartley theorem gives the channel capacity of a continuous, band-limited channel corrupted by additive white Gaussian noise (AWGN) as:

C = B · log₂(1 + S/N)  bits/second

Here B is the channel bandwidth in Hz, S is the average received signal power, N is the average noise power, and S/N is the signal-to-noise ratio. The theorem states that C is the theoretical maximum rate at which information can be transmitted through the channel with arbitrarily low probability of error.

The formula shows that capacity grows linearly with bandwidth (double B, roughly double C) but only logarithmically with SNR (each doubling of SNR adds a fixed number of bits/sec, showing diminishing returns) — this is why engineers generally prefer adding bandwidth over pushing signal power when trying to raise data rates cheaply.

Q11 · Numerical
A channel has bandwidth B = 3 kHz and SNR = 1000. Find its channel capacity.
★★★★ 5 Marks numerical

Using Shannon-Hartley: C = B log₂(1+S/N) = 3000 × log₂(1+1000) = 3000 × log₂(1001).

log₂(1001) ≈ 9.97, so C ≈ 3000 × 9.97 ≈ 29,910 bits/sec ≈ 29.9 kbps.

Q12 · Numerical (dB variant)
A channel has bandwidth B = 4 kHz and SNR = 20 dB. Find the channel capacity.
★★★★ 5 Marks numerical

Step 1 — convert SNR from dB to linear: SNR(dB) = 10 log₁₀(S/N) → 20 = 10 log₁₀(S/N) → S/N = 102 = 100.

Step 2 — apply Shannon-Hartley: C = 4000 × log₂(1+100) = 4000 × log₂(101) ≈ 4000 × 6.658 ≈ 26,633 bits/sec ≈ 26.6 kbps.

Always convert dB to a linear ratio first — plugging the dB number directly into log₂() is a common and costly exam error.

Q13 · Theory + Derivation
State and explain Shannon's Channel Coding Theorem (Shannon's Second Theorem). What does it prove and what does it NOT tell us?
★★★★★ 10 Marks — most important theory question in whole unit

Shannon's Channel Coding Theorem states that for a discrete memoryless channel with capacity C: if the transmission rate R ≤ C, there exists a coding scheme for which the probability of decoding error can be made arbitrarily close to zero by increasing the code's block length, while keeping R fixed. Conversely, if R > C, reliable transmission is fundamentally impossible, regardless of how sophisticated the encoder/decoder design is.

What it proves: reliable communication over a noisy channel is achievable — a revolutionary and counter-intuitive result when first published in 1948, since intuition suggests any real noisy channel must always introduce some irreducible error rate.

What it does NOT tell us: the theorem is a pure existence proof — it guarantees a good code exists for any R ≤ C, but gives no construction method. This gap motivated decades of coding-theory research (Hamming, cyclic, convolutional, Turbo, LDPC codes) aimed at finding practical, implementable codes that approach this theoretical promise.

The theorem also establishes C as a sharp threshold: performance doesn't degrade gradually as R crosses C — below C, error-free-in-the-limit transmission is achievable, and above C it is categorically impossible.

Q14 · Applied Numerical
A channel's capacity is 26.6 kbps. Using the Channel Coding Theorem, comment on whether reliable transmission is possible at R = 20 kbps and at R = 30 kbps.
★★★ 5 Marks

At R = 20 kbps: since R = 20 kbps < C = 26.6 kbps, the condition R ≤ C is satisfied, so by the Channel Coding Theorem a coding scheme exists that can drive the error probability arbitrarily close to zero (with sufficiently long code blocks) while transmitting at this rate.

At R = 30 kbps: since R = 30 kbps > C = 26.6 kbps, reliable transmission is not possible — no matter how the code is designed, some irreducible error probability must remain when the rate exceeds capacity.

Q15 · Theory
What is meant by the "Shannon Limit"? Why can no practical system exceed it, and how close have real codes gotten?
★★★ 5 Marks

The Shannon Limit is another name for the channel capacity C itself — the absolute maximum data rate at which information can be transmitted over a channel with arbitrarily low probability of error, given the channel's bandwidth and noise characteristics.

No coding scheme, however sophisticated, can communicate reliably above this rate, because it is a fundamental information-theoretic bound derived from the physics of the channel (bandwidth and noise power) — not merely a limitation of current engineering or algorithm design.

In its most extreme form (infinite bandwidth), the limit reduces to the famous Eb/N₀ ≥ −1.6 dB bound — the minimum energy per bit needed for reliable communication under any circumstances. Modern practical codes such as Turbo codes and LDPC codes (used in 4G/5G/WiFi) now operate within roughly 0.5 dB of this theoretical floor, which is considered one of the great engineering achievements of modern communications.

Q16 · Conceptual Linking
Explain the relationship between channel capacity, the channel coding theorem, and the Shannon limit.
★★★ 5 Marks — conceptual linking question, frequently combined into one

These three ideas describe the same underlying boundary from three different angles, moving from definition → proof → practical naming.

Channel capacity C is the quantitative definition of the limit — the Shannon-Hartley formula C = B log₂(1+S/N) tells us exactly what that maximum rate is for a given continuous AWGN channel.

The Channel Coding Theorem is the proof that this number C is achievable — it shows that reliable (arbitrarily-low-error) transmission is possible for any rate R ≤ C, and impossible for R > C, establishing C as a hard, sharp threshold rather than a soft guideline.

The Shannon Limit is simply the practical, colloquial name engineers use for this same capacity boundary when discussing how close real-world codes (Turbo, LDPC) can get to the theoretical maximum — so all three terms ultimately point to one single number, C, viewed respectively as a formula, a guarantee, and a design target.
