01. Hierarchical Task Analysis (HTA) HIGH
Breaking a big goal into small, doable steps — the backbone of task modelling.
Definition

Hierarchical Task Analysis (HTA) is a technique for analysing a task by decomposing it into a hierarchy of goals, sub-goals, operations and plans — starting from an overall goal at the top and successively breaking it down into smaller, more concrete sub-tasks until each sub-task is simple enough to describe as a single, indivisible operation.

🇮🇳 Hinglish Explanation
HTA ka basic idea simple hai — koi bhi bada task (goal) lo aur usko chhote-chhote sub-tasks mein todte jao, jab tak har sub-task itna simple na ho jaye ki use ek single action/operation ke roop mein describe kiya ja sake. Jaise "chai banana" ek goal hai — isko "paani garam karna", "patti daalna", "doodh milana" jaise sub-goals mein todte hain. Yeh ek top-down decomposition approach hai.

Core Building Blocks of HTA

ElementMeaning
GoalA state of affairs the user wants to achieve (numbered 0 for the top goal, 1, 2, 3… for sub-goals)
Sub-goalA goal that is part of a larger goal — can itself be broken down further
OperationA basic, indivisible action performed by the user to satisfy a goal (the "leaf" of the tree)
PlanDescribes the order/condition in which sub-goals must be carried out to satisfy the parent goal (sequence, selection, or iteration)
Plan Notation Examples

Plan 0: Do 1, then 2, then 3 — (sequence)
Plan 1: Do 1.1, then either 1.2 or 1.3 depending on condition — (selection)
Plan 2: Do 2.1 then repeatedly do 2.2 until done — (iteration)

Fig 1: HTA decomposition of goal "Make a cup of tea" into sub-goals, operations and plans (numbered notation)

Steps to Conduct an HTA

  1. 1. Identify the overall goal of the task.
  2. 2. Collect data (interviews, observation, existing documentation) about how the task is performed.
  3. 3. Decompose the goal into 4–8 sub-goals (the "rule of thumb" range).
  4. 4. Sequence the sub-goals with a plan describing order/conditions.
  5. 5. Decide the appropriate stopping point — stop decomposing when a sub-goal is a single, well-understood operation.
  6. 6. Check the analysis — validate with real users/experts, then redraft if necessary.
🇮🇳 Hinglish
HTA banate waqt ek golden rule follow hota hai — "stopping rule". Jab analyst ko lagta hai ki further break-down karna zaroorat se zyada detail hoga (jaise "hand ko cup ki taraf move karo" jaisi micro-level cheez), tab wahi decomposition rok di jaati hai. Yeh depend karta hai analysis ke purpose par.
Advantages of HTALimitations of HTA
Simple, systematic, widely used and easy to learnDoes not capture cognitive processes (thinking, decision making) well
Good for identifying training needs & interface requirementsCan become very large/unwieldy for complex systems
Flexible stopping rule adapts to purpose of analysisMainly captures observable actions, not user goals/motivation deeply
Provides a clear, hierarchical, graphical representationNo standard/formal notation for concurrency between tasks
⚠ Important

HTA is the most frequently asked topic from this unit — remember the numbering convention (0 for top goal), the 4 core elements (Goal, Sub-goal, Operation, Plan), and be ready to draw a complete tree diagram for a given task (e.g., ATM withdrawal, online shopping, ticket booking).

02. Engineering Task Models MEDIUM

Definition

An Engineering Task Model is a formal, structured, and often notation-based representation of the tasks a user needs to perform with a system, created using systematic engineering methods so that the model can be analysed, validated, reused, and even used to automatically generate or evaluate the user interface — going beyond the informal tree diagrams of basic HTA.

🇮🇳 Hinglish
HTA ek informal/hand-drawn tree hoti hai. Lekin jab hum bade, complex, ya safety-critical systems (jaise aircraft cockpit, medical device) design karte hain, tab humein zyada rigorous aur formal task models chahiye hote hain jinko tools se analyse/validate kiya ja sake. Isi formal engineering approach ko "Engineering Task Models" kehte hain — inme task types, temporal relationships, aur constraints sab kuch precisely define kiye jaate hain.

Why Move from Informal HTA to Engineering Task Models?

AspectInformal HTAEngineering Task Model
NotationFree-hand tree + plain-English plansFormal, standardised notation with defined semantics
ConcurrencyNot well supportedExplicit temporal operators (sequence, choice, parallelism, etc.)
Tool supportMostly manual/drawing toolsCASE tools (e.g. CTTE for CTT) allow simulation & validation
ReusabilityLow — tied to one analyst's interpretationHigh — models can be shared, reused, and linked to UI generation

Common Purposes of Engineering Task Models

  • Requirements capture — precisely record what users need to do
  • Design guidance — drive the structure of menus, dialogs, and screens
  • Usability evaluation — compare actual usage against the intended model to spot deviations
  • Model-based UI generation — some tools can auto-generate a prototype interface directly from the task model
  • Documentation — serve as a communication artefact between designers, developers and stakeholders
Where This Leads

The most widely taught and RTU-relevant engineering/formal task-modelling notation is the Concur Task Tree (CTT), discussed in detail next — it takes the hierarchical spirit of HTA and adds a rigorous notation for describing temporal/concurrency relationships between tasks.

03. Concur Task Trees (CTT) HIGH

Definition

ConcurTaskTrees (CTT), proposed by Fabio Paternò, is a graphical, hierarchical task-modelling notation that extends classical task trees (like HTA) with a formal set of temporal operators to precisely describe how sibling tasks in the tree relate to each other in time — including sequencing, choice, concurrency (parallelism), and interruption — while also classifying every task by who performs it.

🇮🇳 Hinglish
CTT ek advanced version hai task-tree ka jisme HTA jaisi hierarchy toh hai hi, saath hi har do sibling tasks ke beech exact temporal relationship (kaunsa task pehle, kaunsa saath-saath, kaunsa optional) ko special symbols se describe kiya jaata hai. Yeh multi-user ya complex concurrent systems (jaise chat app, jahan "typing" aur "receiving message" saath-saath ho sakte hain) model karne ke liye best hai.

Task Types in CTT (classified by "who performs it")

Task TypeIcon/SymbolDescription
User TaskCirclePurely cognitive/physical action performed by the user without the system (e.g. deciding which option to pick)
Application (System) TaskSquare/BoxPerformed entirely by the system, invisible input from the user (e.g. system validates a password)
Interaction TaskTriangle/Rounded boxPerformed by the user through the interface — a physical action that has immediate effect on the system (e.g. clicking a button)
Abstract TaskDiamond/PentagonComplex tasks requiring more than one type of activity, or task not yet fully specified — usually decomposed further

CTT Temporal Operators (Between Sibling Tasks)

OperatorSymbolMeaning
EnablingT1 >> T2T1 must complete before T2 can start (sequence)
Enabling with info passingT1 []>> T2T1 finishes and passes data/information to T2
ChoiceT1 [] T2Either T1 or T2 occurs, not both — user/system picks one
Concurrency (Interleaving)T1 ||| T2T1 and T2 can happen in any order/simultaneously, independently
Concurrency with sync.T1 |[]| T2T1 and T2 run concurrently but must synchronise at certain points
DisablingT1 [> T2T2 permanently interrupts and terminates T1
Suspend-ResumeT1 |> T2T2 temporarily interrupts T1; T1 resumes later from where it stopped
IterationT1*T1 repeats zero or more times
Finite IterationT1(n)T1 repeats exactly n times
Optionality[T1]T1 is optional — may or may not be performed
Order IndependenceT1 |=| T2Both T1 and T2 must occur, in either order, but not simultaneously

04. Introduction to Formalism in Dialog Design MEDIUM

Definition

Dialog Design is the process of specifying the structure and sequencing of the conversation (turn-taking) between the user and the system — which inputs are legal at which point, what the system responds with, and how control moves between different states/screens of the interface. A formalism in this context is a mathematically precise notation (a set of symbols and rules) used to unambiguously model this dialog structure, so it can be analysed, verified and communicated without ambiguity.

🇮🇳 Hinglish
Dialog design basically yeh define karta hai ki user aur system ke beech "conversation" kaise chalegi — user kab kya input de sakta hai, system kaise respond karega, aur ek screen/state se doosri screen/state mein kaise move hoga. Isko sirf words mein likhna ambiguous ho sakta hai, isliye hum formal notations (jaise diagrams/mathematical models) use karte hain taaki design bilkul clear aur testable ho — koi confusion na ho.

Why Do We Need Formal Notations for Dialog Design?

  • Precision — removes ambiguity present in natural-language descriptions
  • Analysability — can mathematically check for unreachable states, deadlocks, or missing transitions
  • Communication — gives designers, developers, and testers a shared, unambiguous reference
  • Simulation — many formal models can be "executed"/simulated before the real system is built
  • Consistency checking — ensures every state has a defined response to every possible user action

Common Formal Notations Used in Dialog Design

NotationCore IdeaBest Suited For
State Transition Networks / FSMDialog as a set of states with labelled transitions triggered by eventsSimple, mostly-sequential dialogs (e.g. wizards, menus)
State Charts (Statecharts)FSM extended with hierarchy (nested states) and concurrency (AND-states)Complex dialogs with many modes and overlapping activities
Petri NetsPlaces (conditions) + transitions (events) + tokens (current state markers)Dialogs needing explicit modelling of concurrency & synchronisation
Grammar-based notations (BNF)Dialog described as production rules, similar to programming-language grammarsCommand-line/textual dialog syntax
Event-Response / Production SystemsA flat set of "if event-then action" rules, no explicit stateSimple reactive systems, small dialog boxes
⚠ Important — RTU Focus

Out of these, RTU syllabus specifically expects deep coverage of the three state-based/net-based formalisms: FSM, State Charts, and (classical) Petri Nets — covered in full detail in the next three sections.

05. Finite State Machines (FSM) in Dialog Design HIGH

Definition

A Finite State Machine (FSM), also called a State Transition Diagram/Network, is a formal model consisting of a finite set of states, a set of events/inputs, and a transition function that determines, for each state and each event, which single new state the system moves to — used in dialog design to represent all the possible "modes" of the interface and the legal moves between them.

🇮🇳 Hinglish
FSM ek simple aur bahut popular formalism hai jisme system hamesha kisi ek "state" (situation) mein hota hai — jaise "Idle", "Logged In", "Error". Jab koi event hota hai (jaise button click), system ek defined transition follow karke doosri state mein chala jaata hai. Ismein ek waqt mein sirf ek hi state active hoti hai — isliye concurrency (do cheezein saath mein) achhe se model nahi hoti.

Formal Components of an FSM

ComponentMeaning
States (S)Finite set of distinct situations/modes the system can be in
Events/Inputs (E)Finite set of triggers (user actions, system signals) that can cause a state change
Transition Function (δ)Maps (current state, event) → next state
Initial StateThe state the system starts in
Final/Accepting State(s)State(s) marking successful completion of the dialog (optional)
FSM = (S, E, δ, s0, F)
where S = set of states, E = set of events, δ: S×E → S, s0 = initial state, F = set of final states

Advantages of FSMLimitations of FSM
Simple, easy to draw and understandState-explosion problem — number of states grows exponentially as independent features are added
Formal enough to detect unreachable/dead statesPoor at modelling concurrency — only one state active at a time
Directly implementable as code (switch/case or table-driven)No built-in way to express hierarchy/grouping of related states
Good for simple, largely sequential dialogs (wizards, menus)Repeated sub-dialogs (e.g. "confirm" screen reused everywhere) must be duplicated
The State-Explosion Problem — Example

Suppose a text editor dialog has 3 independent toggle features: Bold (on/off), Italic (on/off), Underline (on/off). Modelled as flat FSM states, this needs 2×2×2 = 8 separate states just to represent the combinations — and adding a 4th toggle doubles it again to 16. This explosion is exactly what State Charts (next section) were invented to solve.

06. State Charts in Dialog Design HIGH

Definition

State Charts (Statecharts), introduced by David Harel, are a visual formalism that extends classical FSMs with three key extra features — hierarchy (states can be nested inside super-states), concurrency (a state can be split into independent parallel/AND regions active at the same time), and broadcast communication (an event in one region can trigger a transition in another) — enabling compact, scalable modelling of complex, multi-mode reactive dialogs.

🇮🇳 Hinglish
Statechart, FSM ka hi upgraded/improved version hai jo state-explosion problem solve karta hai. Isme states ko group/nest kar sakte hain (super-state ke andar sub-states) aur ek hi time pe multiple independent regions parallel chal sakti hain (jaise Bold aur Italic dono independently on/off ho sakte hain bina alag-alag combination states banaye). Isse diagram chhota, clean aur scalable ban jaata hai.

Key Extensions Over Plain FSM

FeatureWhat It Solves
Hierarchy (Super-states)Group related sub-states inside one super-state; a transition out of the super-state applies to all sub-states at once — avoids repeating the same transition on every sub-state
Concurrency (AND-states)Split a state into 2+ independent parallel regions (orthogonal components), each with its own sub-states — directly fixes the state-explosion problem
History StateRemembers which sub-state was active before an interruption, so the system can resume exactly where it left off
Broadcast CommunicationAn event fired in one region can be "heard" and trigger transitions in other concurrent regions

Statecharts are the notation behind UML State Machine Diagrams — remember Harel's name, and be ready to explain the three fixes (hierarchy, concurrency, broadcast) with the state-explosion example above for a 10-mark question.

07. Classical Petri Nets in Dialog Design HIGH

Definition

A (Classical) Petri Net is a formal, graphical and mathematical modelling notation, invented by Carl Adam Petri, consisting of two types of nodes — places (representing conditions/states) and transitions (representing events/actions) — connected by directed arcs, with tokens residing in places to indicate the current condition of the system; a transition "fires" (executes) only when all its input places contain a token, consuming those tokens and producing new tokens in its output places, which makes Petri nets naturally suited to modelling concurrency, synchronisation and resource-sharing in dialogs.

🇮🇳 Hinglish
Petri Net mein do tarah ke nodes hote hain — Places (circle, condition/state ko represent karta hai) aur Transitions (bar/rectangle, event/action ko represent karta hai). Places ke andar tokens (dots) hote hain jo batate hain ki system abhi kaunsi condition mein hai. Ek transition tabhi "fire" hoga jab uske saare input places mein token maujood ho — fire hote hi input places ke tokens hat jaate hain aur output places mein naye tokens aa jaate hain. Yeh model concurrency aur synchronization (jaise do parallel processes ka ek point pe milna) dikhane ke liye best hai.

Formal Components of a Petri Net

ComponentSymbolMeaning
PlaceCircleRepresents a condition, state, or resource availability
TransitionBar / RectangleRepresents an event or action that can occur
TokenDot inside a placeIndicates that the corresponding condition currently holds
ArcDirected arrowConnects places to transitions (input) or transitions to places (output); never place-to-place or transition-to-transition
Petri Net = (P, T, F, M0)
where P = set of places, T = set of transitions, F = set of directed arcs (flow relation) ⊆ (P×T) ∪ (T×P), M0 = initial marking (token distribution)

Firing Rule

A transition t is enabled if every place connected to it by an incoming arc contains at least one token. When an enabled transition fires: one token is removed from each input place, and one token is added to each output place. This single rule is enough to model sequencing, branching, and — most importantly — synchronisation of concurrent activities.

Why This Matters for Dialog Design

Neither plain FSM nor even a basic statechart can as elegantly express "wait until both concurrent tasks complete" as a Petri net does — the mere geometric requirement that T2 needs tokens from both P2 and P3 captures the synchronisation rule directly and visually.

Advantages of Petri NetsLimitations of Petri Nets
Excellent, natural modelling of concurrency and synchronisationCan become visually complex for large dialogs
Strong mathematical foundation — supports formal analysis (reachability, deadlock detection)Steeper learning curve than simple FSM diagrams
Can model resource contention/sharing naturally (tokens = limited resources)Not as directly/simply implementable in code as an FSM table
FSM vs Petri Net — Quick Difference
FeatureFSMPetri Net
Basic elementsStates + transitionsPlaces + transitions + tokens
Active "state" representationExactly one state active at a timeMultiple places can hold tokens simultaneously
Concurrency modellingPoorNatural & explicit (via multiple tokens/places)
Synchronisation modellingNot directly possibleDirect — a transition waits for tokens in all input places

Q1 · 10 MARKS

What is Hierarchical Task Analysis? Explain its components with a suitable example.

Hierarchical Task Analysis (HTA) is a technique that decomposes an overall goal into a hierarchy of sub-goals, operations and plans, starting broad and becoming progressively more detailed until each unit is a simple, indivisible operation.

Components: Goal (numbered 0 for top-level), Sub-goal (numbered 1, 2, 3…), Operation (leaf-level indivisible action), and Plan (describes the order/condition for carrying out sub-goals — sequence, selection, or iteration).

Example: Goal 0 "Withdraw Cash from ATM" → Plan 0: do 1-2-3-4 → 1. Insert card, 2. Enter PIN, 3. Select amount, 4. Collect cash & card. Each of these can be decomposed further (e.g. 2.1 Type digits, 2.2 Press enter).

Q2 · 10 MARKS
10 MARKS
What is ConcurTaskTree (CTT)? Explain its task types and temporal operators with diagrams.

CTT is a formal, hierarchical task-modelling notation proposed by Fabio Paternò that extends HTA-style trees with precise temporal operators describing how sibling tasks relate in time, and classifies every task by who performs it.

Task types: User task (circle), Application/System task (box), Interaction task (rounded shape), Abstract task (diamond).

Key operators: Enabling (T1 >> T2), Choice (T1 [] T2), Concurrency (T1 ||| T2), Disabling (T1 [> T2), Iteration (T1*), Optionality ([T1]).

Example: In a login dialog, "Enter Credentials" >> "Validate" [> "Cancel", where entering username and password within Credentials happens as Username ||| Password.

Q4 · 10 MARKS
10 MARKS
Explain the need for formalism in dialog design. Discuss FSM as a dialog design formalism with its advantages and limitations.

Formal notations remove ambiguity from natural-language dialog descriptions, allow mathematical analysis (unreachable states, deadlocks), give a shared reference for designers/developers, and can be simulated/executed before implementation.

FSM models a dialog as a finite set of states with a transition function δ: S×E→S mapping (current state, event) to the next state; formally FSM = (S, E, δ, s0, F).

Advantages: Simple, easy to draw, directly implementable, good for sequential dialogs.

Limitations: State-explosion problem for independent features, poor concurrency support (only one active state at a time), no hierarchy/grouping.

Q5 · 10 MARKS
10 MARKS
What are State Charts? How do they overcome the limitations of FSM? Explain with an example.

Statecharts, introduced by David Harel, extend FSM with hierarchy (nested super-states), concurrency (AND-states/parallel regions), and broadcast communication between regions.

They overcome FSM's state-explosion problem: a super-state split into N independent concurrent regions of k states each needs only N×k states drawn, instead of k^N states in a flat FSM.

Example: A text-editor's Bold/Italic/Underline toggles need 8 flat FSM states (2³ combinations) but only 3 concurrent regions of 2 states each (6 states total) in a statechart — and the saving grows further as more independent toggles are added.

Q6 · 10 MARKS
10 MARKS
Explain classical Petri Nets. Define its components and firing rule, and describe why it is suitable for dialog design.

A Petri Net is a formal graphical/mathematical notation with two node types — Places (conditions/states, drawn as circles) and Transitions (events/actions, drawn as bars) — connected by directed arcs, with tokens in places showing the current condition.

Formal definition: Petri Net = (P, T, F, M0), where P=places, T=transitions, F=flow relation (arcs), M0=initial marking.

Firing rule: A transition is enabled only when every input place holds a token; firing removes one token from each input place and adds one to each output place.

Suitability for dialog design: Petri nets naturally model concurrency and synchronisation — a transition can be made to wait for tokens from multiple concurrent activities, directly representing "wait until both parallel tasks finish" style dialog logic that FSM and even statecharts express less directly.

Write a short note on Engineering Task Models.

Engineering Task Models are formal, structured, tool-supportable representations of user tasks (beyond informal HTA trees) used for precise requirements capture, design guidance, usability evaluation, and even model-based automatic generation of user interfaces. Q9 · 5 MARKS
5 MARKS
List and explain the CTT temporal operators for Enabling, Choice, Concurrency and Iteration.

Enabling (T1 >> T2): T1 must fully complete before T2 can begin.

Choice (T1 [] T2): Either T1 or T2 happens, exclusively — never both.

Concurrency (T1 ||| T2): T1 and T2 can occur in any order or simultaneously, independent of each other.

Iteration (T1*): T1 may repeat zero or more times.

Q10 · 5 MARKS
5 MARKS
What is the "state-explosion problem" in FSM-based dialog design?

The state-explosion problem occurs when independent, orthogonal features of a dialog are each modelled as extra states in a flat FSM — the total number of states grows multiplicatively (2^n for n independent binary toggles), quickly making the diagram unmanageably large. For example, 3 independent toggle features require 2³=8 flat FSM states, and a 4th toggle would double this to 16. Statecharts solve this using concurrent (AND) regions.
