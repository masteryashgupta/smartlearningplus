2.1 Historical Evolution of the Field High

English

The historical evolution of HCI traces how the mode of interaction between humans and computers has shifted — from expert-only, hardware-level control in the 1950s to today's natural, touch- and voice-based interaction accessible to virtually anyone — driven by advances in hardware, changes in who uses computers, and growing understanding of human cognition.

Hinglish

Pehle computers sirf scientists/engineers use karte the, switches aur punch cards ke through. Aaj ek 5 saal ka bachcha bhi tablet use kar leta hai bina padhe. Yeh jump kaise hua — yehi is topic mein padhenge: CLI se GUI, GUI se touch, touch se voice/gesture tak.

Milestones Worth Remembering
  • 1963: Ivan Sutherland's Sketchpad — the first program with a graphical, interactive interface.
  • 1968: Douglas Engelbart's "Mother of All Demos" — introduced the mouse, hypertext, and windows.
  • 1973: Xerox Alto at Xerox PARC — first computer built around a GUI with WIMP elements.
  • 1984: Apple Macintosh — first commercially successful mass-market GUI computer.
  • 2007: Apple iPhone — mainstreamed multi-touch gesture interaction.

2.2 Interactive System Design High

English

An interactive system is a computer-based system that engages in an ongoing dialogue with a user — accepting input, processing it, and producing output that the user can perceive and respond to in real time. Interactive system design is the process of designing this dialogue so that it matches the user's tasks, expectations, and cognitive abilities.

Hinglish

Interactive system woh hai jisme "conversation" chalti hai — tum kuch karte ho (click/type), system react karta hai, tum uska response dekh kar next action lete ho. Interactive system design ka matlab hai is poore "dialogue" ko itna smooth banana ki user ko soch-soch kar kaam na karna pade.

Components of an Interactive System

  • User: The human with a goal, prior knowledge, and expectations.
  • Input Devices: Keyboard, mouse, touchscreen, microphone, sensors — channels through which the user acts.
  • Dialogue / System Core: The logic that interprets input, updates internal state, and decides what to present back.
  • Output Devices: Screen, speaker, haptic feedback — channels through which the system communicates back.
  • Feedback Loop: The continuous cycle connecting user action to system response and back.

Fig 2.2 — Structure of an Interactive System: User → Input Device → Dialogue/System Core → Output Device → back to User

Interaction Styles

StyleDescriptionExample
Command LineUser types text commands with specific syntaxUNIX/Linux terminal, DOS
Menu SelectionUser picks an option from a displayed listRight-click context menu
Form Fill-inUser enters data into labelled fieldsRegistration form, KYC form
Direct ManipulationUser acts directly on visible objects (drag, resize, click)Dragging a file to a folder, resizing a window
WIMPWindows, Icons, Menus, Pointer combinedWindows/macOS desktop
Natural LanguageUser speaks or types in everyday languageSiri, ChatGPT, Alexa
Gesture-basedUser interacts via touch or body movementSwipe on phone, VR hand tracking
Hinglish

Har interaction style ka apna use-case hai — power users (developers) CLI prefer karte hain kyunki fast hai, lekin naye users ke liye GUI/menu better hai kyunki options dikhte hain, guess nahi karna padta. Isliye ek achha designer apne target users ke hisaab se style choose karta hai.

📌 Design Tip: There is no single "best" interaction style — the right choice depends on the user's expertise, the task's frequency, and the need for speed vs. discoverability. Expert-repetitive tasks favour command-based styles; infrequent or novice tasks favour menus and direct manipulation.

2.3 Concept of Usability — Definition and Elaboration High

English (ISO 9241-11 Definition)

Usability is defined as "the extent to which a product can be used by specified users to achieve specified goals with effectiveness, efficiency, and satisfaction in a specified context of use." It is not an inherent, fixed property of a system — it depends on who is using it, for what task, and under what conditions.

Hinglish

Usability ka matlab sirf "easy to use" nahi hai — ISO definition ke hisaab se 3 cheezein matter karti hain: (1) kaam ho raha hai ya nahi (effectiveness), (2) kitni jaldi/kam effort mein ho raha hai (efficiency), (3) user ko use karke kaisa lag raha hai (satisfaction). Ek app expert ke liye usable ho sakti hai lekin beginner ke liye nahi — isliye "context of use" bhi important hai.

Nielsen's Five Usability Attributes

AttributeMeaningExample / How to Measure
LearnabilityHow easily first-time users accomplish basic tasksTime taken by a new user to complete their first transfer in a banking app
EfficiencyHow quickly experienced users perform tasks once learnedNumber of clicks/seconds an expert trader takes to place an order
MemorabilityHow easily users re-establish proficiency after a period of not using the systemCan a user who hasn't opened the app in a month still navigate it?
ErrorsHow many errors users make, how severe they are, and how easily they recoverRate of "wrong order type selected" mistakes and undo availability
SatisfactionHow pleasant the system is to use, subjectivelyPost-task survey rating (e.g., System Usability Scale — SUS)

Fig 2.3 — Nielsen's Five Usability Attributes forming the pillars of overall Usability

Usability vs User Experience (UX)

AspectUsabilityUser Experience (UX)
FocusCan the user complete the task efficiently and without error?How does the user feel about the entire journey — emotion, delight, trust?
ScopeNarrower — the interface/interaction itselfBroader — includes branding, support, onboarding, emotional response
Measured byTask success rate, time-on-task, error countSatisfaction surveys, Net Promoter Score, emotional response
RelationshipUsability is a necessary subset of UX — a system can be usable but still have a poor overall experience (e.g., usable but ugly or untrustworthy).

2.4 HCI and Software Engineering Medium

English

Traditional Software Engineering (SE) follows a largely linear, specification-driven process (e.g., the Waterfall model), whereas HCI requires an iterative, user-centered process because user needs and usability problems are often only discovered once people actually interact with the system. Integrating HCI into SE means embedding user research, prototyping, and usability evaluation as first-class activities in the development lifecycle, not as an afterthought.

Hinglish

Normal software engineering mein hum requirements likhte hain, design karte hain, code karte hain, test karte hain — ek seedhi line mein. Lekin usability ka pata tabhi chalta hai jab real user use karta hai. Isliye HCI process mein baar-baar design → test with users → redesign ka loop chalta hai, jab tak interface acha na ho jaye.

The Star Life Cycle Model (Hartson & Hix)

Unlike the Waterfall model's fixed sequence, the Star Life Cycle model for HCI design allows movement between any two adjacent activities, with Evaluation at the centre — every activity's output is evaluated (often with users) before moving to the next, and designers can jump back to any prior activity based on evaluation results.

Fig 2.4 — Star Life Cycle Model: Evaluation sits at the centre and connects to every activity, allowing iterative movement instead of a fixed linear sequence

Waterfall (Traditional SE) vs User-Centered Design (HCI)

AspectWaterfall ModelUser-Centered Design (UCD)
FlowStrictly sequential: Requirements → Design → Code → Test → MaintainIterative loop: Analyze → Design → Prototype → Evaluate → repeat
User involvementMainly at requirements stage onlyContinuous — users are tested at every iteration
Change costExpensive late-stage changes (after coding)Cheap early-stage changes (caught during prototype testing)
Best suited forWell-understood, stable requirements (e.g., backend/API systems)User-facing systems where needs emerge through testing (dashboards, apps)
📌 Exam Tip: A common exam question asks you to explain why HCI cannot simply "plug into" the Waterfall model. The core reason: usability problems are usually invisible until real users interact with a working (or prototyped) system — so HCI needs early, cheap, repeatable evaluation cycles that Waterfall's late-stage testing does not provide.

2.5 GUI Design and Aesthetics High

English

A Graphical User Interface (GUI) is an interface that lets users interact with a system through visual elements — windows, icons, menus, and a pointer (the WIMP paradigm) — instead of typed text commands. Aesthetics in GUI design refers to the visual quality of the interface (layout, color, typography, spacing) and its influence on perceived usability — commonly summarized as the "aesthetic-usability effect", where users perceive visually pleasing designs as easier to use, even if actual usability is unchanged.

Hinglish

GUI ka matlab hai visual elements se interact karna — buttons, icons, menus — bajaye commands type karne ke. Aesthetics ka matlab hai interface "dekhne mein" kaisa lagta hai — colors, spacing, fonts sahi hain ya nahi. Research batati hai ki agar design achha dikhta hai, toh users usko "easy to use" bhi maan lete hain — chahe functionally kuch change na hua ho. Isliye visual design bhi utna hi important hai jitna functionality.

Core GUI Components (WIMP)

ElementPurposeExample
WindowsBounded, movable/resizable regions containing contentApp window, dialog box
IconsSmall graphical symbols representing objects/actionsFolder icon, trash icon, buy/sell icon
MenusLists of selectable commands/optionsFile menu, right-click context menu
PointerOn-screen indicator controlled by mouse/touch for selectionCursor, finger tap point

Beyond WIMP, modern GUIs also use widgets like buttons, checkboxes, radio buttons, dropdowns, sliders, tabs, and toast notifications.

Principles of Visual Aesthetics (CRAP / CARP Principles)

  • Contrast: Differentiate important elements (primary buttons, alerts) using color/size/weight so they stand out.
  • Repetition: Reuse consistent visual patterns (same button style, same spacing) across the interface for predictability.
  • Alignment: Every element should line up with something else — creates a clean, organized, scannable layout.
  • Proximity: Group related items close together and separate unrelated ones — reduces cognitive load in parsing the screen.

2.6 Prototyping Techniques High

English

A prototype is an early, simplified representation of a system built to explore design ideas, test usability, and gather user feedback before investing in full-scale implementation. Prototyping is the practice of building and iterating on such representations throughout the design process.

Hinglish

Prototype ek "rough model" hota hai — poora system bina bnaye pehle uska ek chhota, simple version bana lete hain taaki user se early feedback mil jaye. Isse costly mistakes early stage mein hi pakdi ja sakti hain, poore code likhne ke baad nahi.

Low-Fidelity vs High-Fidelity Prototypes

AspectLow-Fidelity (Lo-Fi)High-Fidelity (Hi-Fi)
Detail levelRough sketches/wireframes, no colors or real contentNear-final visuals, real colors, fonts, sometimes real data
Speed to createVery fast (minutes to hours)Slower (hours to days)
Cost of changeVery cheap — just redrawExpensive — rebuild interactive elements
Best used forEarly idea exploration, quick stakeholder discussionUsability testing close to final experience, stakeholder sign-off
Tools/MethodPaper & pen, whiteboard, basic wireframe toolsFigma, Adobe XD, coded HTML/CSS prototypes

Prototyping Approaches

ApproachDescriptionWhen to Use
Throwaway (Rapid) PrototypingBuilt quickly to test an idea, then discarded — not reused in the final productEarly-stage concept validation, unclear requirements
Evolutionary PrototypingPrototype is incrementally refined and becomes part of (or evolves into) the final systemRequirements fairly well understood, want continuous delivery
Vertical PrototypingImplements one feature/flow fully (all layers), leaving others unbuiltTesting feasibility or usability of one critical, complex feature
Horizontal PrototypingImplements the surface/UI layer of all features, but without real backend logicTesting overall navigation and information architecture
Example — Applied to a Trading Dashboard

Before building a real-time price alert panel, a designer might first sketch it on paper (Lo-Fi, throwaway) to decide layout, then build a clickable Figma mockup (Hi-Fi, horizontal — just the UI, no real Socket.IO feed) to test with a few traders, and only after positive feedback start coding the actual React component connected to the live feed (evolutionary/vertical prototype that becomes the real feature).

Key takeaway for Unit 2: HCI evolved from rigid, expert-only command interfaces to natural, universally accessible interaction — and this evolution is driven by continuously applying usability principles, iterative (not linear) design processes borrowed into Software Engineering, careful GUI/aesthetic design, and low-cost prototyping to catch usability problems before expensive development begins.
Hinglish Trick

Nielsen 5 Usability Goals (LEMES): "Learn Everyday, Make Error-free Software" (Learnability, Efficiency, Memorability, Error tolerance, Satisfaction).
Prototypes: Horizontal = UI ki sabhi screens ki shallow chaudaai. Vertical = Ek single feature ki poori depth (Front-to-Back)!

❓ Unit 2 — Q&A (RTU Exam Pattern)

Unit 2 · Theory
Q1. Explain the historical evolution of Human-Computer Interaction with major milestones. ★★★ 10 Marks
10 Marks

HCI evolved through distinct eras: batch processing in the 1950s with no direct interaction, followed by time-sharing systems and Ivan Sutherland's Sketchpad (1963) — the first interactive graphical program. Command Line Interfaces dominated the 1970s alongside Xerox PARC's invention of the mouse and windows at the Alto (1973).

The 1980s introduced the GUI/WIMP paradigm commercially via the Apple Macintosh (1984). The 1990s brought web and multimedia interaction, the 2000s ubiquitous/mobile computing, and 2007 onward multi-touch gesture interaction via the iPhone. The present era is defined by natural voice interaction (Siri, Alexa) and emerging immersive/gesture interfaces (AR/VR).

Unit 2 · Theory
Q2. What is an interactive system? Explain its components and common interaction styles. ★★★ 5 Marks
5 Marks

An interactive system engages in ongoing dialogue with a user, accepting input and producing perceivable output in real time. Its core components are the User, Input Devices, the Dialogue/System Core, Output Devices, and the Feedback Loop connecting them.

Common interaction styles include command line, menu selection, form fill-in, direct manipulation, WIMP, natural language, and gesture-based interaction — each suited to different user expertise levels and task frequencies.

Unit 2 · Theory
Q3. Define usability as per ISO 9241-11. Explain Nielsen's five usability attributes. ★★★ 10 Marks
10 Marks

ISO 9241-11 defines usability as the extent to which specified users can achieve specified goals with effectiveness, efficiency, and satisfaction in a specified context of use — meaning usability is context-dependent, not an absolute property of a system.

Nielsen's five attributes elaborate this: Learnability (ease for first-time users), Efficiency (speed for experienced users), Memorability (ease of regaining proficiency after a break), Errors (frequency, severity, and recoverability of mistakes), and Satisfaction (subjective pleasantness of use).

Unit 2 · Conceptual
Q4. Differentiate between Usability and User Experience (UX). ★★ 3 Marks
3 Marks

Usability focuses narrowly on whether a user can complete tasks effectively, efficiently, and without error, measured through task success rate, time-on-task, and error count. UX is broader, covering the user's overall emotional journey — including branding, trust, and delight — measured through satisfaction surveys and metrics like Net Promoter Score. Usability is a necessary subset of good UX.

Unit 2 · Theory
Q5. Explain the relationship between HCI and Software Engineering. Describe the Star Life Cycle model. ★★★ 10 Marks
10 Marks

Traditional Software Engineering follows a largely linear process (e.g., Waterfall), while HCI requires iterative, user-centered development because usability issues typically surface only once real users interact with the system. Integrating HCI into SE means embedding user research, prototyping, and evaluation throughout the lifecycle rather than only at the end.

Hartson and Hix's Star Life Cycle model places Evaluation at the centre, connected to every other activity (task/functional analysis, requirements specification, conceptual/design, prototyping, implementation) — allowing designers to move between any two adjacent activities based on evaluation results, rather than following one fixed sequence.

Unit 2 · Theory
Q6. What is GUI? Explain the WIMP paradigm and the key principles of visual aesthetics. ★★★ 5 Marks
5 Marks

A Graphical User Interface (GUI) lets users interact through visual elements rather than typed commands, built around the WIMP paradigm — Windows, Icons, Menus, and Pointer.

Key aesthetic principles (CRAP/CARP) are Contrast (making important elements stand out), Repetition (consistent visual patterns for predictability), Alignment (elements lining up for a clean layout), and Proximity (grouping related items together) — together reducing cognitive load and improving perceived usability via the aesthetic-usability effect.

Unit 2 · Theory
Q7. What is prototyping? Differentiate between low-fidelity and high-fidelity prototypes. ★★ 5 Marks
5 Marks

A prototype is an early, simplified representation of a system built to explore design ideas and gather feedback before full implementation. Low-fidelity prototypes (paper sketches, wireframes) are fast and cheap to change, ideal for early idea exploration, while high-fidelity prototypes (Figma mockups, coded prototypes) closely resemble the final product and are used for usability testing close to the real experience, though they cost more to modify.

Unit 2 · Conceptual
Q8. Differentiate between throwaway and evolutionary prototyping, and between vertical and horizontal prototyping. ★★ 5 Marks
5 Marks

Throwaway (rapid) prototyping is built quickly to validate an idea and then discarded, suited to unclear early requirements, while evolutionary prototyping is incrementally refined and becomes part of the final system, suited to well-understood requirements.

Vertical prototyping fully implements one feature across all layers to test feasibility, whereas horizontal prototyping implements the UI layer across all features without real backend logic, used to test overall navigation and information architecture.
