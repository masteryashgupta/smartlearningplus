📗 UNIT 2 — Introduction to Compilers

Objective, Scope, Outcome · Compiler/Translator/Interpreter · Phases · Bootstrapping · Finite Automata Lexical Analyzer · Token Recognition · LEX · Error Handling  |  Hours: 06

English

A Compiler is a program that translates source code written in a high-level programming language into an equivalent program in a low-level target language (usually machine or assembly code), reporting any errors found during translation. This unit covers the foundational concepts: definitions of compiler/translator/interpreter, the phases a compiler goes through, and the first real compiler phase — Lexical Analysis.

Hinglish

Ye unit Compiler Design ka foundation hai. Sabse pehle samjhenge ki Compiler, Translator aur Interpreter mein kya farak hai. Phir dekhenge ki ek compiler internally kitne phases (stages) mein kaam karta hai. Sabse important part — Lexical Analysis — jo source code ko chhote-chhote meaningful pieces (tokens) mein todta hai. Ye unit RTU exam mein bahut heavily poochha jaata hai.

1. Compiler, Translator & Interpreter — Definitions High ⭐⭐⭐⭐⭐

English

Compiler: A program that translates an entire source program written in a high-level language into an equivalent target program (usually machine code), all at once, before execution begins.

Translator: A general term for any program that converts code from one language (source) to another language (target). A compiler, interpreter, and assembler are all types of translators.

Interpreter: A program that directly executes source code instructions one statement at a time, without producing a separate target file — it translates and executes simultaneously, line by line.

Hinglish

Compiler: Pura source code ek baar mein translate karke ek executable file bana deta hai (jaise .exe). Phir us file ko run karo. C/C++ compilers (GCC) is tarah kaam karte hain.
Translator: Ek umbrella term hai — koi bhi program jo ek language ko dusri language mein convert kare, "translator" kehlaata hai. Compiler, interpreter, assembler — sab translator ki categories hain.
Interpreter: Line-by-line code ko directly execute karta hai, bina pehle se ek alag executable file banaye. Python isi tarah kaam karta hai — har line padhta hai aur turant execute karta hai.

Compiler vs Interpreter — Comparison Table High ⭐⭐⭐⭐⭐ (Guaranteed every year)

Note

Many modern languages use a hybrid approach: Java compiles to bytecode (compiler phase) which is then interpreted/JIT-compiled by the JVM (interpreter + just-in-time compiler). Python similarly compiles to bytecode (.pyc) before interpretation. So "pure" compilers/interpreters are increasingly rare in practice.

2. Phases of a Compiler High ⭐⭐⭐⭐⭐ (Most Important — diagram + explanation guaranteed)

English

A compiler translates source code to target code through a sequence of six phases, each performing a specific, well-defined transformation: Lexical Analysis, Syntax Analysis, Semantic Analysis, Intermediate Code Generation, Code Optimization, and Code Generation. A Symbol Table and Error Handler interact with every phase.

Hinglish

Compiler ek single step mein kaam nahi karta — ye 6 phases mein source code ko process karta hai, har phase ka apna specific kaam hai. Pehle phase tokens banaata hai, dusra grammar check karta hai, teesra meaning check karta hai, aur aage badhte hue eventually machine code generate hota hai. Symbol Table har phase ke saath interact karti hai (variables/functions ki info store karne ke liye), aur Error Handler har phase mein errors detect karta hai.

Fig 2.1 — The 6 phases of a compiler, with Symbol Table Manager and Error Handler interacting with every phase. This is the most commonly drawn diagram in RTU exams.

Description of each phase (with examples for: x = a + b * c):
  1. Lexical Analyzer (Scanner): Reads source code character-by-character and groups them into tokens (meaningful units). For "x = a + b * c": tokens are id(x), =, id(a), +, id(b), *, id(c).
  2. Syntax Analyzer (Parser): Takes the token stream and checks if it follows the language's grammar rules; builds a parse tree / syntax tree representing the grammatical structure.
  3. Semantic Analyzer: Checks for semantic correctness — type checking, scope rules, ensuring operations make sense (e.g., can't add a string to an integer in a type-strict language). Builds an annotated syntax tree.
  4. Intermediate Code Generator: Converts the syntax tree into an intermediate representation (e.g., Three Address Code) that's easier to optimize and is closer to machine code, but still machine-independent.
  5. Code Optimizer: Improves the intermediate code to make it run faster or use less memory, without changing its meaning (removes redundant computations, dead code, etc.).
  6. Code Generator: Converts optimized intermediate code into the final target code (assembly or machine code), handling register allocation and instruction selection.
Example — Tracing all 6 phases for: x = a + b * c

Hinglish

Ye example bohot important hai — RTU mein aksar exact yahi type ka question aata hai (kisi simple expression ko lekar sab 6 phases dikhao). Yaad rakho ki har phase ek specific kaam karta hai: tokens banana, grammar check karna, type check karna, intermediate code banana, optimize karna, aur finally assembly/machine code generate karna.

Symbol Table & Error Handler Medium ⭐⭐⭐

English

The Symbol Table is a data structure that stores information about identifiers (variables, functions, classes) used in the program — name, type, scope, memory location. It is consulted and updated by nearly every phase. The Error Handler detects, reports, and (where possible) recovers from errors at each phase (lexical errors, syntax errors, semantic errors).

Hinglish

Symbol Table ek data structure hai jisme har variable/function ka naam, type, scope, memory location store hota hai. Almost har phase isse read/write karta hai. Error Handler har phase mein errors pakadta hai — jaise undefined variable, syntax mistake, type mismatch — aur error messages deta hai (kabhi-kabhi recovery bhi try karta hai taaki compilation aage continue ho sake).

3. Bootstrapping Medium ⭐⭐⭐

English

Bootstrapping is the technique of writing a compiler for a language using that same language itself, then using a simpler/existing compiler (often written in another language, or a smaller subset) to compile this self-hosting compiler the first time. After this initial compilation, the compiler can compile itself in subsequent versions.

Hinglish

Bootstrapping ka concept thoda confusing lagta hai pehli baar mein — basically: agar tumhe ek C compiler khud C mein likhna hai, to chicken-egg problem hai (C compiler chahiye C compiler banane ke liye!). Solution: pehle ek chhota subset wala C compiler kisi aur language (jaise assembly) mein likho. Use use karke apna full C compiler (jo C mein likha hai) compile karo. Ab ye naya compiler khud ko future mein compile kar sakta hai — "bootstrap" ho gaya!

Fig 2.2 — Bootstrapping: use an existing compiler to build the first version of a new self-hosting compiler.

4. Lexical Analysis — Review of Finite Automata High ⭐⭐⭐⭐⭐ (Most Important Topic in Unit 2)

English

Lexical Analysis (also called Scanning) is the first phase of a compiler. It reads the source program character by character and groups characters into meaningful sequences called lexemes, producing a token for each lexeme. Lexical analyzers are implemented using finite automata (FA) — each token type corresponds to a regular expression, and the FA recognizes strings matching that pattern.

Hinglish

Lexical Analysis ka kaam hai — source code ko character by character padhna aur usse chhote meaningful groups (tokens) mein todna. Jaise "int x = 5;" ko tokens mein todo: int (keyword), x (identifier), = (operator), 5 (number), ; (punctuation). Ye recognition internally Finite Automata (FA) use karke hota hai — har token type ka apna pattern (regular expression) hota hai, aur FA us pattern ko match karta hai.

Key Terms: Token, Lexeme, Pattern High ⭐⭐⭐⭐⭐

English

Token: A category/class name representing a group of lexemes (e.g., id, num, keyword).
Lexeme: The actual sequence of characters in the source code that matches a token's pattern (e.g., "counter", "42", "while").
Pattern: The rule (often a regular expression) describing the set of strings that can form a particular token (e.g., letter followed by letters/digits for identifiers).

Hinglish

Ye teeno terms exam mein bahut confuse karti hain — yaad rakhne ka tarika: Token = category ka naam (jaise "identifier"). Lexeme = actual text jo source code mein likha hai (jaise "counter"). Pattern = rule jo batata hai ki kaunsi strings is token mein aa sakti hain (jaise "letter follow by letters/digits").

Finite Automata for Token Recognition High ⭐⭐⭐⭐

English

A Finite Automaton (FA) is a mathematical model used to recognize patterns. Lexical analyzers convert each token's regular expression into a Deterministic Finite Automaton (DFA) via NFA construction (Thompson's construction + subset construction). The DFA reads input characters, transitions between states, and accepts the input if it ends in a final/accepting state.

Hinglish

FA basically ek state machine hai jo input characters padh ke states ke beech move karta hai. Agar end mein "accepting state" pe pahunch jaaye, to wo string token ke pattern se match karti hai. Lexical analyzer banane ka standard process: Regular Expression → NFA (Thompson's Construction) → DFA (Subset Construction). Ye TOC subject se directly connect hota hai!

Fig 2.3 — DFA recognizing identifiers: a letter, followed by zero or more letters/digits. S1 (double circle) is the accepting state.

States neededFewer states, simpler to construct from regexMore states (subset construction), but faster execution

5. Input Buffering Medium ⭐⭐⭐

English

Input Buffering is a technique used to speed up the scanning process by reading large blocks of source code into memory buffers at once (rather than character by character from disk), reducing the number of slow I/O operations. The classic technique uses two buffers (often each of size N, e.g., 4096 bytes) with a special sentinel character (eof) placed at the end of each buffer to efficiently detect buffer boundaries.

Hinglish

Agar lexical analyzer har character disk se ek-ek karke padhe, to ye bahut slow hoga (disk I/O expensive hai). Isliye buffering use hoti hai — ek baar mein bada chunk (jaise 4KB) memory mein load karo, phir wahan se fast access karo. Two-buffer scheme mein do buffers hote hain, aur ek sentinel character (special marker, jaise EOF) har buffer ke end mein lagaya jaata hai taaki "buffer khatam ho gaya" ye check fast ho jaaye (without checking buffer-end condition on every single character).

Fig 2.4 — Two-buffer scheme: lexemeBegin marks the start of current lexeme, forward scans ahead. Sentinels avoid checking buffer boundary on every character.

6. Recognition of Tokens High ⭐⭐⭐⭐

English

Token recognition uses Transition Diagrams — flowchart-like representations of the finite automaton for a token pattern, with states (circles) and labeled edges (transitions on specific input characters). The lexical analyzer simulates these diagrams to identify which token type a sequence of input characters belongs to.

Hinglish

Transition diagrams DFA jaise hi hote hain — states (circles) aur edges (transitions) ka use karke batate hain ki kaunse characters aane par kaunsa state jaayenge. Lexer in diagrams ko follow karke decide karta hai ki current lexeme kaunsa token hai. RTU mein relational operators (<, <=, <>, =, >, >=) ka transition diagram bahut common numerical/diagram question hai!

Fig 2.5 — Transition diagram for relational operators. * = accepting states (each recognizes a different token: <=, <>, <, =, >=, >). "other*" means retract one character (lookahead) before accepting.

Key concept — Lookahead / Retraction:

When the automaton reads one character too many to decide the token (e.g., reading '<' then a non-'=' character to confirm it's just "<" not "<="), it must retract (push back) that extra character so it can be read again as part of the next token. This is why some transitions are marked "other*" with retraction.

7. LEX — A Lexical Analyzer Generator High ⭐⭐⭐⭐⭐

English

LEX is a tool (lexical analyzer generator) that automatically generates a lexical analyzer (scanner) in C from a specification file containing regular expressions and corresponding actions. The programmer writes patterns for each token type; LEX compiles these into an efficient DFA-based scanner, removing the need to hand-code the lexer.

Hinglish

LEX ek tool hai jo khud lexical analyzer banata hai — tumhe manually DFA code likhne ki zaroorat nahi! Tum bas regular expressions aur unke corresponding actions (kya karna hai jab wo pattern match ho) likhte ho ek .l file mein, aur LEX use compile karke ek C program (lex.yy.c) bana deta hai jo automatically tokens recognize karta hai. Ye bahut time-saving tool hai compiler development mein.

Structure of a LEX Program High ⭐⭐⭐⭐⭐ (Diagram + structure commonly asked)

A LEX source file (.l) has three sections separated by %%:

Declarations Section %% Translation Rules (Pattern → Action) %% Auxiliary Functions / User Code
  • Declarations Section: C declarations, macro definitions, and header includes go here (between %{ and %}).
  • Translation Rules: Each rule is a pattern (regex) and an action (C code) — when input matches the pattern, the action executes.
  • Auxiliary Functions: Additional C functions (e.g., main()) used by the actions, plus the mandatory call to yylex() to start scanning.
Example — Simple LEX program to count vowels and lines
%{ int vowel_count = 0, line_count = 0; %} %% [aeiouAEIOU] { vowel_count++; } \n { line_count++; } %% int main() { yylex(); printf("Vowels: %d, Lines: %d\n", vowel_count, line_count); return 0; }

Fig 2.6 — LEX compilation pipeline: lex.l → lex.yy.c (via lex/flex) → compiled with C compiler → executable lexer that scans input and produces tokens.

8. Error Handling in Lexical Analysis High ⭐⭐⭐⭐

English

Lexical errors occur when the scanner encounters a sequence of characters that doesn't match any valid token pattern (e.g., an illegal character, a malformed number). Since few errors are purely lexical (most show up as syntax errors later), the lexer typically performs minimal local correction and reports the error so compilation can continue.

Hinglish

Lexical errors tab hote hain jab scanner ko aisa character sequence milta hai jo kisi bhi valid token pattern se match nahi karta — jaise koi illegal symbol (@#$ jo language mein support nahi). Lexer usually error report karta hai aur kuch simple recovery technique use karke aage badhta hai, taaki sirf ek error ke wajah se poora compilation na ruk jaaye.

Error Recovery Strategies High ⭐⭐⭐⭐

StrategyDescription
Panic ModeDelete successive characters from the erroneous input until a well-formed token is found (simplest, most common in lexical analysis).
DeletionDelete one extra/illegal character and retry.
InsertionInsert a missing character that was likely omitted (e.g., missing closing quote).
ReplacementReplace an incorrect character with the correct one (e.g., typo correction).
TranspositionSwap two adjacent characters that appear to be in wrong order.
Example — Lexical error scenarios
  • Illegal character: x = a @ b; — '@' is not a valid operator → lexer reports "illegal character '@'" and may skip it (panic mode).
  • Unterminated string: printf("hello); — missing closing quote → lexer may insert assumed closing quote or report error at end of line.
  • Malformed number: 3.14.15 — two decimal points → lexer reports malformed numeric literal.
Hinglish

Panic Mode sabse common recovery technique hai lexical analysis mein — bas tab tak characters skip karte raho jab tak ek valid token na mil jaaye. Ye approach simple hai aur compilation ko crash hone se bachata hai — bas error report karke aage badh jaate hain.

Summary — Unit 2 Key Takeaways High

  • Compiler = whole-program translation; Interpreter = line-by-line execution; Translator = umbrella term for both.
  • 6 Phases: Lexical → Syntax → Semantic → Intermediate Code → Optimization → Code Generation, with Symbol Table & Error Handler throughout.
  • Bootstrapping: building a self-hosting compiler using an existing compiler.
  • Lexical Analysis: source code → tokens, implemented via Finite Automata (DFA from regex via NFA).
  • Token vs Lexeme vs Pattern — category vs actual text vs rule.
  • Input Buffering: two-buffer scheme with sentinels for fast scanning.
  • LEX: automatic lexical analyzer generator from regex + action specifications.
  • Error handling: panic mode is the standard lexical error recovery strategy.
Hinglish Trick

Lexical Terms: Pattern = Niyam / Formula (Regex). Lexeme = Actual text jo code mein likha hai (e.g. "total"). Token = Category tag jo parser ko milta hai (e.g. ID).
LEX Sections: "DRU" (Declarations %% Rules %% User C Code).

Start at state 0. Unit 2 · Concept
Q7. Explain Input Buffering technique used in lexical analysis. ★★★ 5 Marks
5 Marks

Input buffering speeds up scanning by reading large chunks of source code into memory buffers (instead of one character at a time from disk). The classic two-buffer scheme uses two buffers each of size N (e.g., 4096 bytes), with a sentinel character (eof) placed at the end of each buffer. Two pointers — lexemeBegin (start of current lexeme) and forward (scans ahead) — move through the buffers. The sentinel allows a single comparison to detect both end-of-buffer and end-of-file, avoiding a separate boundary check on every character.

Unit 2 · Concept
Q9. What is a lexical error? Explain different error recovery strategies in lexical analysis. ★★★★ 5-7 Marks
7 Marks

A lexical error occurs when the scanner encounters character sequences that don't match any valid token pattern (e.g., illegal symbols, malformed numbers).

Recovery strategies: (1) Panic mode — delete characters until a valid token is found (most common). (2) Deletion — remove an extra illegal character. (3) Insertion — insert a likely missing character. (4) Replacement — substitute an incorrect character. (5) Transposition — swap adjacent out-of-order characters.

Goal: report the error but allow compilation to continue scanning rest of the program (rather than stopping entirely at first error).

Unit 2 · Comparison
Q10. Differentiate between NFA and DFA in the context of lexical analysis. ★★★ 5 Marks
5 Marks

NFA (Non-deterministic Finite Automaton): multiple/epsilon transitions possible from a state on the same input; constructed directly from regex via Thompson's Construction; fewer states but slower to simulate.

DFA (Deterministic Finite Automaton): exactly one transition per state per input symbol; constructed from NFA via Subset Construction; more states but faster simulation since no backtracking needed.

Lexical analyzers typically convert regex → NFA → DFA for actual implementation, since DFA gives faster, single-pass scanning. Full comparison table given above.
