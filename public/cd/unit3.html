📙 UNIT 3 — Parsing & Context-Free Grammars

Review of CFG · Ambiguity of Grammars · Top-Down Parsing (LL, Recursive Descent, Predictive) · Bottom-Up Parsing (Shift-Reduce, LR, SLR, Canonical LR, LALR) · Ambiguous Grammar Parsing · Operator Precedence Parsing · YACC & Error Handling  |  Hours: 10

English

Parsing (Syntax Analysis) is the compiler phase that takes the stream of tokens produced by the lexical analyzer and determines whether they form a syntactically valid program according to the language's grammar — represented as a Context-Free Grammar (CFG). The parser builds a parse tree (or equivalent structure) representing this grammatical derivation. This is the heaviest, most numerical-intensive unit in the entire subject — RTU questions here are almost always parsing-table construction problems.

Hinglish

Ye unit Compiler Design ka sabse bada aur sabse important unit hai (10 hours, sabse zyada weightage). Lexical analyzer ne tokens bana diye, ab Parser ka kaam hai check karna ki ye tokens grammar ke rules follow karte hain ya nahi. Do approaches hain — Top-Down (root se shuru karke leaves tak) aur Bottom-Up (leaves se shuru karke root tak). RTU mein har approach ke numerical questions (parsing table banana) bahut zyada poochhe jaate hain — isliye practice zaroor karo!

1. Review of Context-Free Grammar (CFG) High ⭐⭐⭐⭐

English

A Context-Free Grammar (CFG) is a 4-tuple G = (V, T, P, S) where: V = set of non-terminals (variables), T = set of terminals (tokens), P = set of production rules of the form A → α (where A ∈ V and α is a string of terminals/non-terminals), and S = start symbol (S ∈ V).

Hinglish

CFG ek formal way hai language ki grammar define karne ka. Non-terminals = abstract symbols jo further expand ho sakte hain (jaise Expression, Statement). Terminals = actual tokens (id, +, *, num). Productions = rules batate hain ki ek non-terminal kis tarah expand hoga. Start symbol = jahan se derivation shuru hoti hai. Ye TOC subject se directly connect hota hai!

Example — Simple expression grammar
E → E + T | T T → T * F | F F → ( E ) | id

Here: V = {E, T, F}, T = {+, *, (, ), id}, S = E.

Derivation: Leftmost & Rightmost High ⭐⭐⭐⭐

English

A derivation is a sequence of production applications starting from S, eventually producing a string of terminals. In a Leftmost Derivation (LMD), the leftmost non-terminal is always expanded first. In a Rightmost Derivation (RMD), the rightmost non-terminal is always expanded first.

Hinglish

LMD mein hamesha sabse left wala non-terminal expand karte hain. RMD mein hamesha sabse right wala. Same string ke liye dono derivations alag order mein steps lenge lekin end result same hoga. Top-down parsers LMD use karte hain, bottom-up parsers RMD ko reverse order mein follow karte hain.

Parse Tree Medium ⭐⭐⭐

English

A parse tree is a graphical representation of a derivation. The root is labeled with the start symbol; each internal node represents a non-terminal being expanded; leaves (read left to right) form the derived string. Both LMD and RMD of the same string produce the same parse tree — only the order of expansion differs.

2. Ambiguity of Grammars High ⭐⭐⭐⭐⭐ Most Asked

English

A grammar is said to be ambiguous if there exists at least one string in the language for which more than one parse tree can be constructed — equivalently, if it has more than one leftmost derivation (or more than one rightmost derivation) for the same string.

Hinglish

Agar ek hi string ke liye ek se zyada parse tree ban sakte hain, to grammar ambiguous kehlati hai. Yeh compiler ke liye problem create karta hai kyunki compiler ko nahi pata chalta ki kaunsa interpretation sahi hai. Classic example: E → E+E | E*E | id — string "id+id*id" ke liye 2 alag parse trees ban sakte hain (different precedence ke saath).

Example — Ambiguous grammar
E → E + E | E * E | id

For string "id+id*id", two different parse trees are possible — one which groups "+" first ((id+id)*id) and one which groups "*" first (id+(id*id)) — giving two different leftmost derivations, hence ambiguity.

Fig 3.2 — Two different parse trees for "id+id*id" using the same ambiguous grammar — proof of ambiguity

Removing Ambiguity High ⭐⭐⭐⭐ — Numerical/Conversion Question

Ambiguity is typically removed by rewriting the grammar to enforce precedence and associativity rules explicitly, using a layered (precedence-cascading) grammar:

E → E + T | T (lowest precedence: +) T → T * F | F (higher precedence: *) F → ( E ) | id (highest precedence: parentheses/atoms)

This forces "*" to bind tighter than "+", removing the ambiguity while generating the exact same language.

⚠ Important

Ambiguity is a property of the grammar, not the language — the same language can often be described by both an ambiguous and an unambiguous grammar. The classic "dangling else" problem (if-then-else nesting) is another famous ambiguity example, frequently asked in RTU exams.

3. Introduction to Parsing High ⭐⭐⭐⭐

English

Parsing is the process of analyzing a sequence of tokens to determine its grammatical structure with respect to a given CFG. There are two fundamental strategies: Top-Down Parsing (constructing the parse tree from the root/start symbol down to the leaves, attempting to derive the input string) and Bottom-Up Parsing (constructing the parse tree from the leaves up to the root, attempting to reduce the input string back to the start symbol).

Hinglish

Parsing ka matlab hai input tokens ko grammar ke against verify karna aur unka structure (parse tree) banana. Do main strategies: Top-Down — start symbol se shuru karke input string derive karte hain. Bottom-Up — input tokens se shuru karke unhe reduce karte-karte start symbol tak pahunchte hain.

4. Top-Down Parsing High ⭐⭐⭐⭐⭐

English

Top-Down Parsing builds the parse tree starting from the root (start symbol) and works downward, at each step trying to match the next input token by choosing the correct production to expand the current non-terminal — essentially attempting to find a leftmost derivation that produces the given input string.

Hinglish

Top-down parsing start symbol se shuru hoti hai, aur step-by-step productions apply karke input string tak "derive" karne ki koshish karti hai. Har step pe yeh decide karna padta hai ki kaunsa production use karna hai — yahi sabse tricky part hai.

4.1 Left Recursion & Its Elimination High ⭐⭐⭐⭐ — Numerical

English

A grammar has left recursion if a non-terminal A has a production of the form A → Aα (direct) — meaning A appears as the leftmost symbol on the right side of its own production. Top-down parsers cannot handle left recursion since they would recurse infinitely trying to expand A before consuming any input.

Elimination Formula
Given: A → Aα | β Rewrite as: A → β A' A' → α A' | ε

Example: E → E+T | T becomes: E → T E' and E' → +T E' | ε

4.2 Left Factoring Medium ⭐⭐⭐

English

Left Factoring is a grammar transformation used when two or more productions for the same non-terminal share a common prefix, making it impossible for a predictive parser to decide which production to use by looking at only the next token. The common prefix is factored out into a new production.

Example
Before: S → if E then S else S | if E then S After: S → if E then S S' S' → else S | ε

4.3 FIRST and FOLLOW Sets High ⭐⭐⭐⭐⭐ — Always Asked

English

FIRST(α) = the set of terminals that begin the strings derivable from α (if α can derive ε, then ε ∈ FIRST(α)). FOLLOW(A) = the set of terminals that can appear immediately to the right of A in some sentential form (if A can be the rightmost symbol, $ ∈ FOLLOW(A)).

Hinglish

FIRST(A) batata hai ki A ko expand karne par sabse pehle kaunsa terminal aa sakta hai. FOLLOW(A) batata hai ki A ke baad kaunsa terminal aa sakta hai. Yeh dono LL(1) parsing table banane ke liye zaroori hain — RTU mein numerical question guaranteed hota hai.

Rules for computing FIRST(X)
  • If X is a terminal, FIRST(X) = {X}.
  • If X → ε is a production, add ε to FIRST(X).
  • If X → Y1Y2...Yk, add FIRST(Y1)−{ε}; if ε∈FIRST(Y1), add FIRST(Y2)−{ε}; continue until some Yi does not have ε in FIRST; if all Y1...Yk have ε, add ε to FIRST(X).
Rules for computing FOLLOW(A)
  • Place $ in FOLLOW(S) where S is the start symbol.
  • If A → αBβ, everything in FIRST(β) except ε is in FOLLOW(B).
  • If A → αB, or A → αBβ where ε∈FIRST(β), then everything in FOLLOW(A) is in FOLLOW(B).
Example — FIRST & FOLLOW for E → TE' | E' → +TE'|ε | T → FT' | T' → *FT'|ε | F → (E)|id
Non-TerminalFIRSTFOLLOW
E{ (, id }{ ), $ }
E'{ +, ε }{ ), $ }
T{ (, id }{ +, ), $ }
T'{ *, ε }{ +, ), $ }
F{ (, id }{ +, *, ), $ }

5. LL Grammars & LL Parser High ⭐⭐⭐⭐⭐

English

An LL(1) Parser is a table-driven, non-backtracking top-down parser. "LL" stands for Left-to-right scan of input, producing a Leftmost derivation, using 1 token of lookahead to decide which production to apply. It uses a parsing table M[A, a] that, for each non-terminal A and lookahead terminal a, specifies which production to use.

Hinglish

LL(1) parser ek table-based parser hai jo sirf 1 token aage dekh kar (lookahead) decide kar leta hai ki kaunsa production use karna hai — bina backtracking ke. "LL" naam isliye kyunki yeh Left-to-right scan karta hai aur Leftmost derivation produce karta hai.

Construction of LL(1) Parsing Table High ⭐⭐⭐⭐⭐ — Most Asked Numerical

Algorithm
  1. For each production A → α, for each terminal a in FIRST(α), add A → α to M[A, a].
  2. If ε ∈ FIRST(α), for each terminal b in FOLLOW(A), add A → α to M[A, b]. If $ ∈ FOLLOW(A), also add A → α to M[A, $].
  3. All undefined entries in M are marked as error.
Example — LL(1) Parsing Table for the grammar above
id+*()$
EE→TE'E→TE'
E'E'→+TE'E'→εE'→ε
TT→FT'T→FT'
T'T'→εT'→*FT'T'→εT'→ε
FF→idF→(E)
⚠ A Grammar is LL(1) if and only if:

For every two productions A → α | β of the same non-terminal: (1) FIRST(α) ∩ FIRST(β) = ∅, and (2) if ε ∈ FIRST(β), then FIRST(α) ∩ FOLLOW(A) = ∅. If the same M[A,a] cell would receive two different productions, the grammar is NOT LL(1) (it has a multiply-defined entry).

5.1 Error Handling in LL Parsers Medium ⭐⭐⭐

English

When the LL(1) parser encounters a blank/error entry in the parsing table M[A,a], or when the top of the stack is a terminal that doesn't match the input symbol, it signals a syntax error. Common recovery strategies include Panic Mode Recovery (skip input tokens until a "synchronizing" token from FOLLOW(A) is found, then pop A and resume) and Phrase-Level Recovery (fill the erroneous table entries with error-handling routines that perform local corrections like inserting a missing token).

Hinglish

Jab parsing table mein blank entry mil jaaye ya stack ka terminal input se match na ho, to error signal hota hai. Panic Mode mein parser tab tak tokens skip karta hai jab tak koi "safe" (FOLLOW set ka) token na mile. Phrase-Level Recovery mein specific error routines define ki jaati hain jo missing token insert ya extra token delete kar sakti hain.

6. Recursive Descent Parsing & Predictive Parsers High ⭐⭐⭐⭐

English

A Recursive Descent Parser is a top-down parser implemented as a set of mutually recursive procedures, one for each non-terminal in the grammar; each procedure attempts to match a specific portion of the input. A Predictive Parser is a special, more efficient form of recursive descent parser that uses one token of lookahead to decide — without any backtracking — exactly which production/procedure call to use at each step.

Hinglish

Recursive Descent Parser har non-terminal ke liye ek function banata hai, jo recursively ek dusre ko call karte hain. Predictive Parser is technique ka improved version hai jisme backtracking ki zaroorat nahi padti — sirf 1 token dekh kar hi sahi production choose ho jaata hai (LL(1) table use karke).

Recursive Descent vs Predictive Parser

FeatureRecursive Descent (General)Predictive Parser
BacktrackingMay require backtrackingNo backtracking (1 lookahead is enough)
ImplementationOne recursive procedure per non-terminalOften table-driven (uses LL(1) table) or recursive with lookahead
Grammar RequirementWorks on any CFG (with backtracking, inefficient)Requires LL(1) grammar
EfficiencyCan be exponential with backtrackingLinear time — O(n)
Example — Recursive Descent procedure for E → TE'
procedure E() { T(); Eprime(); } procedure Eprime() { if (lookahead == '+') { match('+'); T(); Eprime(); } // else: ε production, do nothing }

7. Bottom-Up Parsing High ⭐⭐⭐⭐⭐

English

Bottom-Up Parsing constructs the parse tree starting from the input string (leaves) and works upward toward the start symbol (root) by repeatedly identifying a substring matching the right side of a production and replacing it with the corresponding non-terminal (left side) — this process is called reduction, and it traces out a rightmost derivation in reverse.

Hinglish

Bottom-up parsing input string se shuru hoti hai aur use reduce karte-karte start symbol tak le jaati hai. Har step pe ek "handle" (substring jo kisi production ke RHS se match karta hai) dhundha jaata hai aur use corresponding LHS se replace kiya jaata hai. Yeh process Rightmost Derivation ko reverse order mein follow karta hai.

7.1 Shift-Reduce Parsing High ⭐⭐⭐⭐⭐ — Numerical

English

Shift-Reduce Parsing is a form of bottom-up parsing that uses a stack and an input buffer, performing two main types of actions: Shift (push the next input symbol onto the stack) and Reduce (replace a handle on top of the stack with the non-terminal on the left side of the matching production). Parsing succeeds when the stack contains only the start symbol and the input is empty.

Hinglish

Shift-Reduce parser stack aur input buffer use karta hai. Shift = input se ek symbol uthakar stack pe daal do. Reduce = stack ke top par jo handle (production ka RHS) match ho raha hai, use LHS se replace kar do. Jab stack mein sirf start symbol bache aur input khatam ho jaaye, to parsing successful.

Example — Shift Reduce trace for "id*id" using T → T*F|F, F→id
StackInputAction
$id*id$shift
$id*id$reduce F→id
$F*id$reduce T→F
$T*id$shift
$T*id$shift
$T*id$reduce F→id
$T*F$reduce T→T*F
$T$accept

7.2 Handle Pruning & Conflicts Medium ⭐⭐⭐

A handle is a substring on the stack that matches the RHS of a production AND whose reduction is a valid step toward reducing the input back to the start symbol. Shift-Reduce parsers can face two types of conflicts:

  • Shift-Reduce Conflict: the parser cannot decide whether to shift the next token or reduce the current handle.
  • Reduce-Reduce Conflict: the parser cannot decide which of two or more productions to use for reduction.

8. LR Parsers High ⭐⭐⭐⭐⭐

English

An LR Parser is a bottom-up, table-driven parser. "LR" stands for Left-to-right scan of input, producing a Rightmost derivation in reverse. LR parsers are the most general/powerful class of efficient (linear-time) parsers, capable of handling a larger class of grammars than LL parsers, including most unambiguous CFGs used for programming languages.

Hinglish

LR parser bottom-up, table-driven parser hai jo input ko Left-to-right scan karta hai aur Rightmost derivation ko reverse order mein produce karta hai. LR parsers LL parsers se zyada powerful hote hain — yeh zyada grammars handle kar sakte hain. Inhe state machine (DFA of items) aur 2 tables — ACTION aur GOTO — use karke implement kiya jata hai.

LR Parser Architecture

An LR parser uses a stack containing alternating states and grammar symbols, an input buffer, and two tables:

  • ACTION[s, a]: tells the parser, given state s on top of stack and terminal a as lookahead, whether to shift, reduce, accept, or report error.
  • GOTO[s, A]: tells the parser which state to go to after reducing and exposing non-terminal A on top of the stack.

Types of LR Parsers — Increasing Power

9. Construction of SLR Parsing Tables High ⭐⭐⭐⭐⭐ — Guaranteed Numerical (10 marks)

English

SLR (Simple LR) parsing constructs the ACTION/GOTO tables using LR(0) items (a production with a dot "•" marking how much of it has been seen) organized into canonical collections of item sets via the closure and goto functions, and resolves reduce actions using the FOLLOW set of the non-terminal being reduced.

Hinglish

SLR parsing table banane ke liye sabse pehle LR(0) items (production mein dot lagakar) ke states banaye jaate hain (closure aur goto functions use karke). Phir har state ke liye decide kiya jaata hai ki shift karna hai ya reduce — reduce ke liye FOLLOW set use hota hai. Isi liye ise "Simple" LR kehte hain — yeh sबसe seedha (simple) tarika hai.

Steps for SLR Table Construction EXAM HOT — Write step by step in exam

  1. Augment the grammar: add new start production S' → S.
  2. Compute the canonical collection of LR(0) item sets (I0, I1, ... In) using closure() and goto() functions.
  3. Build the DFA of item sets — states are item sets, transitions are goto(Ii, X).
  4. For each state Ii containing item A → α•aβ (a terminal), if goto(Ii,a)=Ij, set ACTION[i,a] = shift j.
  5. For each state Ii containing a complete item A → α• (dot at end), for every a in FOLLOW(A), set ACTION[i,a] = reduce A→α.
  6. If Ii contains S'→S•, set ACTION[i,$] = accept.
  7. For each non-terminal A, if goto(Ii,A)=Ij, set GOTO[i,A] = j.
  8. All undefined entries = error.
Example — Closure & Goto for grammar S→AA, A→aA|b

I0 = closure({S'→•S}) = { S'→•S, S→•AA, A→•aA, A→•b }

goto(I0, A) = closure({S→A•A}) = { S→A•A, A→•aA, A→•b }

goto(I0, a) = closure({A→a•A}) = { A→a•A, A→•aA, A→•b }

This process continues until no new states are generated, producing the full canonical collection used to build ACTION/GOTO.

⚠ SLR Limitation

SLR can produce reduce-reduce conflicts for grammars where the FOLLOW set is "too broad" — i.e., FOLLOW(A) includes a terminal that should only trigger a reduction in some contexts, not all. Such grammars are not SLR(1) but may still be LALR(1) or CLR(1).

10. Construction of Canonical LR (CLR) & LALR Parsing Tables High ⭐⭐⭐⭐⭐ — Guaranteed Numerical (10 marks)

English

Canonical LR (CLR/LR(1)) parsing uses LR(1) itemsLALR (Look-Ahead LR) parsing is a practical compromise: it builds the same number of states as SLR (by merging LR(1) states that have identical "core" items, differing only in lookaheads), giving more power than SLR with much less memory than CLR.

Hinglish

CLR (Canonical LR) mein har item ke saath ek lookahead terminal bhi attach hota hai — isse reduce decisions zyada accurate hote hain, lekin states bahut zyada ban jaate hain (memory-heavy). LALR in dono ka best balance hai — yeh CLR ke states ko merge kar deta hai (jinke "core" same hain, sirf lookahead alag hai), isse states ki sankhya SLR jitni hi rehti hai lekin power CLR ke kareeb hoti hai. Isiliye YACC jaise real-world tools LALR use karte hain.

LR(1) Item Format

[ A → α • β , a ]

Means: we are trying to parse A→αβ, having seen α already, and "a" is a terminal that could legally follow this entire production in the current parsing context.

Steps for CLR Table Construction EXAM HOT

  1. Augment grammar: add S' → S.
  2. Compute canonical collection of LR(1) item sets using closure() (propagating lookaheads) and goto().
  3. For item [A→α•aβ,b] in state Ii, if goto(Ii,a)=Ij, ACTION[i,a]=shift j.
  4. For item [A→α•,a] in state Ii (complete item), ACTION[i,a] = reduce A→α (using the item's OWN lookahead, not FOLLOW(A)).
  5. If [S'→S•,$] ∈ Ii, ACTION[i,$] = accept.
  6. GOTO[i,A] computed same as SLR/LR(0).

Construction of LALR Table

Build the full canonical LR(1) collection, then merge all states whose "core" (the item set ignoring lookaheads) is identical, combining their lookahead sets via union. This produces the same number of states as SLR/LR(0), but with item-specific lookaheads — more precise than SLR.

11. Parsing with Ambiguous Grammars Medium ⭐⭐⭐

English

Although ambiguous grammars cannot, by definition, have a conflict-free LR parsing table, many useful ambiguous grammars (e.g. for arithmetic expressions without precedence-cascaded rules) can still be parsed efficiently if shift-reduce/reduce-reduce conflicts are resolved using disambiguating rules — typically by specifying operator precedence and associativity directly to the parser generator instead of rewriting the grammar.

Hinglish

Ambiguous grammars LR parsing table mein conflicts create karti hain. Lekin agar hum precedence aur associativity rules explicitly bata dein (jaise YACC mein %left, %right directives se), to parser generator khud hi conflicts resolve kar leta hai — bina grammar ko rewrite kiye. Isse grammar chhoti aur readable rehti hai.

Example — Resolving conflict using precedence

For grammar E→E+E|E*E|id with input "id+id*id" causing a shift-reduce conflict at state with E+E• and lookahead *: since * has higher precedence than +, the parser is told to shift (favoring tighter binding of *) rather than reduce.

12. Operator Precedence Parsing High ⭐⭐⭐⭐

English

Operator Precedence Parsing is a simple, efficient bottom-up parsing technique applicable to a restricted class of grammars called operator grammars (no production has two adjacent non-terminals on the RHS, and no ε-productions). It defines a precedence relation between pairs of terminals — <• (yields precedence), •> (takes precedence), and ≐ (equal precedence) — stored in an Operator Precedence Table, used directly to find handles without building item sets.

Hinglish

Operator Precedence Parsing ek simple bottom-up technique hai jo sirf "operator grammars" pe kaam karti hai (jahan RHS mein 2 consecutive non-terminals nahi hote). Yeh terminals ke beech precedence relations define karta hai aur in relations ko use karke directly handle dhundh leta hai — bina koi complex item-set state machine banaye.

Precedence Relations

RelationMeaning
a <• ba "yields precedence to" b (a comes before, b binds tighter)
a •> ba "takes precedence over" b (a binds tighter, time to reduce)
a ≐ ba and b have equal precedence (typically matching parens)

⚠ Limitation

Operator Precedence Parsing is fast and simple but works only for a small subset of grammars; it has mostly been superseded in practice by LALR(1) parsers (used by YACC), though it remains a popular RTU exam topic due to its simplicity for hand-tracing.

13. Automatic Parser Generator: YACC High ⭐⭐⭐⭐

English

YACC (Yet Another Compiler-Compiler) is a widely used parser generator tool that automatically constructs a LALR(1) parser from a grammar specification, given in a YACC input file containing grammar rules paired with semantic actions (C code) to be executed on each reduction. It is the standard companion tool to LEX (used for lexical analysis), forming a classic LEX+YACC compiler front-end pipeline.

Hinglish

YACC ek tool hai jo grammar rules diye jaane par automatically ek LALR(1) parser generate kar deta hai — hume khud se parsing table banane ki zaroorat nahi padti. YACC file mein grammar rules ke saath C code (semantic actions) likha jaata hai jo har reduction par execute hota hai. LEX (lexical analyzer generator) ke saath milkar yeh poora compiler front-end bana deta hai.

Structure of a YACC Specification File

%{ /* C declarations, header includes */ %} %token ID NUM PLUS TIMES /* token declarations */ %% /* grammar rules with embedded actions */ expr : expr PLUS term { $$ = $1 + $3; } | term { $$ = $1; } ; %% /* auxiliary C code, main() function */
SectionPurpose
DeclarationsC code, token declarations (%token), precedence (%left, %right)
RulesGrammar productions with associated semantic actions in C
Auxiliary CodeSupporting C functions, including main() and yyerror()

13.1 Error Handling in LR Parsers (YACC) High ⭐⭐⭐⭐

English

LR parsers detect a syntax error the moment an ACTION table entry is found to be blank/error for the current state and lookahead — this is a desirable property since LR parsers never perform a single reduction beyond a true syntax error (the "viable prefix" property). YACC provides a special error token that grammar rules can use to specify explicit error-recovery productions.

Hinglish

This rule says: "if a statement can't be parsed normally, skip tokens until a semicolon, report the error, and resume parsing from there."

What is an ambiguous grammar? Show that the grammar E→E+E|E*E|id is ambiguous, and convert it to an unambiguous grammar.

A grammar is ambiguous if some string in the language can be derived by more than one parse tree (equivalently, more than one leftmost derivation). For "id+id*id", two different parse trees exist — one grouping + first, one grouping * first — proving ambiguity. The unambiguous equivalent enforces precedence by cascading rules: E→E+T|T; T→T*F|F; F→(E)|id. This forces * to bind tighter than +, removing all ambiguity while generating the same language.

What is left recursion? Eliminate left recursion from E→E+T|T.

Left recursion occurs when a non-terminal A has a production A→Aα — A appears as the leftmost symbol of its own RHS, causing infinite recursion in top-down parsers. Using the standard elimination formula (A→Aα|β becomes A→βA', A'→αA'|ε), E→E+T|T is rewritten as: E→TE', E'→+TE'|ε.

Explain the steps to construct an SLR parsing table. Construct the SLR table for the grammar S→AA, A→aA|b.

Steps: (1) Augment the grammar with S'→S; (2) compute the canonical collection of LR(0) item sets using closure() and goto(); (3) build the DFA of states; (4) for items A→α•aβ, set ACTION[i,a]=shift to goto(i,a); (5) for complete items A→α•, set ACTION[i,b]=reduce A→α for every b∈FOLLOW(A); (6) accept on S'→S•; (7) GOTO[i,A]=goto(i,A) for non-terminals. Applying this to S→AA, A→aA|b: I0=closure({S'→•S})={S'→•S,S→•AA,A→•aA,A→•b}, and the construction proceeds by computing goto on each symbol (a, b, A, S) from each new state until no new states are generated, then filling ACTION/GOTO from the complete and incomplete items in each state.

What is Operator Precedence Parsing? Explain the three precedence relations used.

Operator Precedence Parsing is a simple bottom-up technique for "operator grammars" (no two adjacent non-terminals on any RHS), using a precedence relation table between terminal pairs to locate handles directly, without building parser states. Three relations: a <• b (a yields precedence to b — b binds tighter), a •> b (a takes precedence over b — time to reduce), and a ≐ b (equal precedence, typically used for matching delimiters like parentheses).

Q8 · 5 MARKS
5 MARKS
What is YACC? Explain the structure of a YACC specification file.

YACC (Yet Another Compiler-Compiler) is a parser generator tool that automatically builds a LALR(1) parser from a grammar specification. A YACC file has three sections separated by %%: (1) Declarations — C code, token declarations, precedence directives; (2) Rules — grammar productions paired with semantic actions in C, executed on reduction; (3) Auxiliary Code — supporting functions including main() and yyerror(). YACC is typically paired with LEX to form a complete compiler front-end.

Q9 · 5 MARKS
5 MARKS
Explain error recovery strategies used in LL and LR parsers.

LL Parsers: Panic Mode Recovery — skip input tokens until a synchronizing token from FOLLOW(A) is found, then resume; Phrase-Level Recovery — fill blank table entries with specific error routines that insert/delete tokens to correct common mistakes locally. LR Parsers: use a special error token in grammar rules (as in YACC) to define explicit recovery productions, e.g. stmt: error ';' skips tokens until a semicolon is found, reports the error, and resumes parsing — LR parsers detect errors immediately (viable-prefix property), never performing an incorrect reduction.

Trace the Shift-Reduce parsing steps (stack, input, action) for the string "id*id" using the grammar T→T*F|F, F→id.

Stack/Input/Action trace: $ / id*id$ / shift → $id / *id$ / reduce F→id → $F / *id$ / reduce T→F → $T / *id$ / shift → $T* / id$ / shift → $T*id / $ / reduce F→id → $T*F / $ / reduce T→T*F → $T / $ / accept. The parser alternates shifting input symbols and reducing handles on the stack until only the start symbol remains and input is exhausted, confirming the string belongs to the language.
